# 05. 시스템 구성 요소의 설계 및 구현: 데이터베이스와 스토리지

데이터베이스는 방대한 데이터를 체계적이고 일관되게 저장하고 관리하며 활용하게 한다. 
크게 관계형과 비관계형으로 나뉘며, 이 장은 키-값 저장소 설계를 깊이 다룬 뒤 DynamoDB, 컬럼 패밀리(HBase), 그래프(Neo4j)로 확장한다.

## 5.1 데이터베이스

- **데이터베이스의 역할**: 데이터를 구조적으로 저장하고, 복잡한 쿼리와 인덱싱으로 빠르게 검색하며, 제약 조건과 검증 규칙으로 무결성을 지키고, 인증과 암호화로 보안을 확보한다. 트랜잭션과 ACID로 동시 접근에도 일관성을 유지하고, 다중화와 백업으로 가용성을 보장한다.
- **핵심 전제**: 하나의 데이터베이스 유형이 모든 요구 사항을 충족할 수는 없으므로, 목적에 맞는 유형을 고르는 것이 설계의 출발점이다.

#### 데이터베이스 유형

- **관계형 vs 비관계형**: 둘 다 데이터를 효율적으로 저장하고 검색하고 관리하는 것이 목표지만 서로 다른 모델과 조회 메커니즘을 쓴다. 데이터 구조, 확장성, 성능이 선택 기준이 된다.

#### 관계형 데이터베이스

- **정의**: 데이터를 행과 열의 표 형식으로 관리하며, 1970년대의 관계형 모델을 기반으로 데이터 요소 간 관계를 정의한다.
- **주요 개념**: 테이블(개체), 행(레코드/튜플), 열(속성/필드), 키(각 행을 구별하는 기본 키와 테이블 간 관계를 잇는 외래 키), 정규화(중복 제거와 무결성), SQL, ACID, 트랜잭션이다.
- **대표 RDBMS**: MySQL, PostgreSQL, Oracle Database, Microsoft SQL Server, SQLite, IBM Db2.
- **용도**: 금융 시스템, 재고 관리, 고객 관계 관리처럼 데이터의 일관성과 구조, 신뢰성이 중요한 분야다.

#### 비관계형 데이터베이스

- **정의**: NoSQL이라고도 하며, 테이블과 행, 열을 쓰는 관계형 모델에서 벗어나 더 유연한 방식으로 비정형과 반정형 데이터를 처리한다.
- **유형**: 키-값 저장소(레디스, DynamoDB, Riak), 문서 지향(MongoDB, CouchDB, RavenDB), 컬럼 패밀리(카산드라, HBase, ScyllaDB), 그래프 기반(Neo4j, 아마존 Neptune, OrientDB)으로 나뉜다.
- **장단점**: 대용량 처리와 확장성, 유연성이 장점이지만, 강력한 데이터 일관성 요구가 낮아지고 더 신중한 데이터 모델링과 인덱싱 설계가 필요하다.

#### 관계형과 비관계형의 장단점

- **관계형 장점**: 데이터 중복 최소화, 강력한 보안 기능, ACID 트랜잭션.
- **관계형 단점**: 복잡한 조인 시 성능 저하, 높은 메모리 소모, 관계와 조인 처리의 복잡성, 수평 확장의 어려움.
- **비관계형 장점**: 정형과 비정형을 모두 다루는 유연한 데이터 모델, 애플리케이션에 영향을 주지 않는 스키마 변경, 뛰어난 수평 확장.
- **비관계형 단점**: 표준화 부족으로 시스템 간 호환성 유지가 어렵고, 대부분 ACID 트랜잭션을 지원하지 않아 일관성이 중요한 작업에서 무결성을 지키기 어렵다.

## 5.2 키-값 저장소

- **정의**: 고유한 키가 특정 값과 연결되는 단순한 저장 방식이다. 대규모 분산 해시 테이블로 이해하면 쉽고, 키-값 쌍이 기본 저장 단위라 읽기와 쓰기 효율이 높다.
- **분산 시스템에서 유용한 이유**: 단순한 구조 덕분에 여러 노드에 쉽게 분산하는 확장성, 매우 빠른 읽기와 쓰기 성능, 고정 스키마가 필요 없는 유연성, 복제와 분할로 확보하는 장애 허용성을 갖춘다.

#### 키-값 저장소 설계의 요구 사항

- **기능 요구 사항**: 키-값 쌍을 삽입하거나 갱신하는 `Put(key, value)`, 키에 연결된 값을 조회하는 `Get(key)`, 키-값 쌍을 삭제하는 `Delete(key)`를 지원해야 한다.
- **비기능 요구 사항**: 데이터를 분산하는 확장성, 낮은 지연 시간의 성능, 노드 장애에도 값을 유지하는 내구성, 최신 쓰기를 읽기에 반영하는 일관성, 노드 장애에도 연산을 처리하는 가용성, 네트워크 장애에도 작동하는 파티션 허용성이다.

## 5.3 확장성과 데이터 복제의 최적화

- **나머지 연산 라우팅의 한계**: 키의 해시 값을 노드 개수로 나눈 나머지로 처리 노드를 정하면 간단하지만, 노드를 추가하거나 제거할 때 나머지가 바뀌어 상당수 키를 다른 노드로 옮겨야 하므로 비용이 크고 지연이 길어진다.

- **일관된 해싱**: 0부터 큰 값까지의 가상 해시 링에 노드와 키를 모두 배치하고, 키의 해시 위치에서 시계 방향으로 가장 가까운 노드가 요청을 처리한다. 노드를 추가하면 바로 다음 노드만 영향을 받아 일부 키만 이동하면 되고, 해시가 무작위로 분포해 부하가 링 전체에 고르게 퍼진다.
    
    <img width="279" height="311" alt="image" src="https://github.com/user-attachments/assets/03f25b5f-8b0f-4302-8e29-0e448a50277d" />
    
- **핫스팟**: 일관된 해싱을 써도 특정 서버가 대용량 데이터를 처리하면 병목이 되어 전체 성능을 떨어뜨린다.
- **가상 노드**: 각 노드에 여러 해시 함수를 적용해 링의 여러 위치에 배치한다. 노드마다 링에서 여러 위치를 차지해 부하가 더 고르게 분산되고, 성능이 좋은 노드에는 가상 노드를 더 많이 할당해 더 많은 요청을 맡길 수 있다. 노드 장애나 서비스 중단, 복귀 시에도 부하가 다른 노드로 고르게 재분산된다.

#### 데이터 복제 전략

- **주종 모델(primary-secondary)**: 하나의 주 저장소가 쓰기를 처리하고 종 저장소가 복제와 읽기를 담당한다. 쓰기 이후 복제되어 복제 지연이 생기고, 주 저장소 장애 시 쓰기가 중단되는 단일 장애점(SPOF) 문제가 있다.
    
    <img width="258" height="251" alt="image" src="https://github.com/user-attachments/assets/58d530e6-611b-4cf1-8ac2-0a9bb05779bd" />
    
- **동등 모델(peer-to-peer)**: 모든 저장소가 읽기와 쓰기를 처리하며 서로 복제해 최신 상태를 유지한다. 전부 복제하면 비효율적이라 보통 노드 3~5개만 골라 복제한다. 지연과 가용성에서 유리하고 단일 장애점을 방지한다.
    
    <img width="275" height="225" alt="image" src="https://github.com/user-attachments/assets/455d380f-7219-441b-aab7-f2103f09a40d" />
    
- **코디네이터와 우선 목록**: 읽기나 쓰기를 처리하는 노드를 코디네이터(coordinator)라 하며 특정 키를 책임진다. 코디네이터는 그 키를 시계 방향의 후속 노드 n-1개에 복제하고, 이 후속 노드들의 목록을 우선 목록(preference list)이라 한다. 복제본이 같은 물리 노드에 몰리지 않도록 이미 포함된 물리 노드의 가상 노드는 제외한다.

## 5.4 get 및 put 함수 구현

- **구성 가능성**: 가용성, 일관성, 비용 효율성, 성능 간 균형을 조정할 수 있는 능력이며, get과 put 연산에 이를 통합한다.
- **노드 선택 방식**: 클라이언트는 요청을 일반 로드 밸런서로 라우팅하거나(코드 종속성 낮음), 분할 인식 클라이언트 라이브러리로 코디네이터 노드에 직접 전달한다(홉 수가 줄어 지연이 낮음).
- **r과 w**: r은 읽기 성공에 필요한 최소 노드 수, w는 쓰기 성공에 필요한 최소 노드 수다. 읽기와 쓰기가 최소 한 노드에서 겹쳐 항상 최신 데이터를 읽으려면 r + w > n을 만족해야 한다.
- **트레이드오프**: r이나 w를 키우면 더 많은 노드의 응답을 기다려 느려진다. r이 클수록 일관성보다 가용성을 우선하는 셈이며, get 지연은 가장 느린 레플리카에 좌우된다.

## 5.5 키-값 저장소의 장애 허용성과 장애 식별

- **엄격한 쿼럼 vs 느슨한 쿼럼**: 엄격한 쿼럼은 정해진 구성원의 동의를 요구해 일관성은 높지만 장애에 민감하고, 잦은 리더 선출이 성능을 떨어뜨린다. 느슨한 쿼럼은 우선 목록에서 정상 동작하는 노드 n개가 읽기와 쓰기를 처리하되, 이 노드들은 링에서 시계 방향으로 이동하며 처음 식별된 노드와 정확히 일치하지 않을 수 있다.
- **힌트 전달(hinted handoff)**: 일시적 장애 처리 기법이다. 쓰기 대상 노드가 접근 불가하면 다른 정상 노드가 요청을 대신 처리하면서 원래 노드용 데이터임을 함께 기록하고, 원래 노드가 복구되면 그 데이터를 전달한 뒤 임시 저장분을 삭제해 레플리카 총수를 유지한다.
- **머클 트리(Merkle tree)**: 영구적 장애에 대비해 레플리카 불일치를 감지하는 자료 구조다. 키-값을 해싱해 리프 노드로 삼고 상위 노드가 자식들의 해시를 저장하는 계층 구조라, 루트 해시부터 비교해 다른 가지만 재귀적으로 탐색하면 전체를 비교하지 않고도 불일치를 찾아 동기화 전송량을 줄인다. 이 안티 엔트로피(anti-entropy) 방식은 데이터 전송과 저장소 접근을 최소화한다. 단, 노드를 추가하거나 삭제하면 키 범위가 바뀌어 트리 해시를 다시 계산해야 한다.
- **노드 구성과 장애 감지**: 대부분의 장애는 일시적이므로 즉시 파티션을 재배치하거나 복구를 시도하지 않는다. 노드 구성 변경은 각 노드에 저장되고 가십 프로토콜(gossip protocol)로 다른 노드와 동기화되어, 두 노드가 무작위로 통신하며 구성 정보를 맞춰 결국 모든 노드가 같은 상태를 공유한다.

## 5.6 시스템 설계 인터뷰: 키-값 저장소 설계

- **범위를 명확히 정의**: 요구 사항과 제한 사항, 대상 규모를 먼저 파악한다.
- **확장성과 성능에 집중**: 데이터와 요청이 늘어도 처리하도록 샤딩이나 일관된 해싱으로 키를 분배하는 방법을 설명한다.
- **레플리카와 일관성**: 고가용성을 위한 레플리카 관리, 일관성 수준, 쓰기 충돌 해결을 언급한다.
- **장애 가능성 대비**: 다중화와 장애 감지, 복구 전략으로 장애 허용성을 확보한다.
- **발전 가능성 고려**: 데이터 버전 관리와 요구 사항 변화에 따른 구성 방안을 제시한다.

## 5.7 DynamoDB

- **정의**: AWS가 제공하는 완전 관리형 서버리스 비관계형 데이터베이스다. SSD 스토리지를 쓰고 지리적으로 분리된 데이터 센터 세 곳에 분산 저장하는 키-값 및 문서형 데이터베이스로, 낮은 지연과 높은 가용성, 내구성을 갖는다.
- **고정 스키마 없음**: 데이터를 읽을 때 스키마를 정의해 유연하다. 여러 테이블로 나누던 데이터를 하나의 문서로 통합해 API 코딩을 간소화하고, 대규모 클러스터에 쉽게 분산해 확장한다.
- **API 함수**: 키 기준으로 추가하거나 덮어쓰는 `PutItem`, 수정하거나 없으면 생성하는 `UpdateItem`, 삭제하는 `DeleteItem`, 조회하는 `GetItem`이다.

#### 데이터 분할과 키

- **수평 분할**: 스키마가 없고 방대한 데이터를 다루므로 여러 저장 서버에 수평으로 나눠 저장하고, 작은 단위로 쪼개 SSD에 담아 빠르게 처리한다.
- **기본 키 유형**: 단일 속성으로 항목을 식별하는 분할 키, 그리고 분할 키에 정렬 키를 결합해 같은 분할 키의 여러 항목을 정렬 키로 구분하는 복합 키가 있다. 분할 키에 해시를 적용해 저장 위치를 정한다.
- **보조 인덱스**: 기본 키 외의 쿼리 키를 써서 조회를 더 유연하게 실행한다.

#### 높은 가용성

- **쓰기 가용성**: 각 파티션을 복제하는 복제 그룹을 두고, 그룹 내 리더 레플리카를 멀티-팍소스로 선출한다. 리더가 쓰기를 처리해 쓰기 전 로그(WAL, Write-Ahead Log)에 기록한 뒤 다른 레플리카로 전파한다. 리더 장애 시에는 쿼럼을 형성할 수 없어 리더의 안정성이 특히 중요하다.
- **읽기 가용성**: 모든 레플리카가 최신 데이터를 동시에 반영하지 않아 기본적으로 최종 일관성을 따른다. 쓰기 직후 최신 값을 즉시 확인하려면 모든 쓰기를 먼저 처리하는 리더 레플리카에 요청해야 한다. 명확히 드러나지 않는 회색 장애는 감지가 어려워, 통신 프로토콜로 리더 상태를 확인한 뒤 선출을 진행한다.

## 5.8 컬럼 패밀리 데이터베이스

- **정의**: 대규모 데이터를 처리하도록 설계된 비관계형 데이터베이스로, 관련 데이터를 컬럼 패밀리라는 그룹으로 묶어 관리하며 와이드 컬럼 스토어(wide-column store)라고도 한다.
- **특징**: 컬럼을 사전 정의 없이 동적으로 추가하고, 클러스터에 노드를 더해 수평 확장하며, 읽기와 쓰기 처리량이 높다. 데이터를 여러 노드에 분산 복제하고, 복잡한 쿼리보다 키 기반 조회에 최적화되어 있으며, 일관성 수준을 조절할 수 있다.
- **대표 예**: 아파치 카산드라는 대규모 분산에 강해 높은 가용성이 필요한 곳에, HBase는 CAP 정리에 따라 가용성을 일부 희생하고 높은 일관성을 유지하는 데 쓰인다.

## 5.9 HBase

- **정의**: HDFS(하둡 분산 파일 시스템)를 기반으로 하고 구글 빅테이블에서 영감을 받은 분산 확장형 비관계형 데이터베이스다. 대규모 데이터를 실시간으로 랜덤 액세스하는 데 강하다.
- **데이터 구성**: 테이블은 여러 행으로, 행은 여러 컬럼 패밀리로, 컬럼 패밀리는 여러 컬럼으로, 컬럼은 키-값 쌍의 모음으로 구성된다.
- **특징**: 범용 하드웨어 클러스터에서 수평 확장하고, 컬럼 패밀리 모델과 강한 일관성(WAL 기반)을 쓰며, 데이터 버전 관리와 자동 부하 분산을 지원한다. 하둡 생태계(MapReduce, 스파크, 하이브)와 연동하고, 블룸 필터와 블록 캐시로 검색을 최적화하며 데이터를 압축한다.

## 5.10 그래프 기반 데이터베이스

- **정의**: 복잡한 데이터 관계를 저장하고 관리하는 데 최적화된 비관계형 데이터베이스로, 노드와 에지로 이뤄진 그래프 구조를 쓴다. 데이터 간 연결을 효율적으로 탐색해 복잡한 관계를 빠르게 조회한다.
- **주요 개념**: 개체를 나타내며 속성을 담는 노드, 노드 간 연관성을 나타내며 속성을 가질 수 있는 에지, 노드와 에지를 분류하는 레이블과 관계 유형이다.
- **특징**: 경로와 연결성, 패턴을 찾는 탐색에 최적화되고, 사이퍼(Cypher) 쿼리 언어로 그래프를 직관적으로 조회하며, 인덱싱으로 성능을 높이고 일부는 수평 확장을 지원한다.
- **용도**: 소셜 네트워크, 추천 엔진, 사기 탐지, 네트워크 관리, 지식 그래프처럼 관계를 모델링하고 분석하는 분야다. 친구의 친구나 공통 관심사 기반 추천 같은 패턴 매칭에 강하다.

## 5.11 Neo4j 그래프 데이터베이스

- **정의**: 복잡한 데이터 관계를 효율적으로 저장하고 빠르게 탐색하는 대표적 그래프 데이터베이스로, 소셜 네트워크와 추천, 사기 탐지, 지식 그래프 등에 특화되어 있다.
- **특징**: 노드와 관계로 데이터를 표현하는 그래프 모델을 쓰고, 노드와 관계 모두 키-값 속성을 가지며, 레이블로 유형을 묶는다. 사이퍼 쿼리 언어로 조회하고, 인덱싱으로 성능을 높이며, 수평 확장과 ACID 준수, 데이터 버전 관리를 지원한다.

## 5.12 관계형 모델링과 그래프 모델링

#### 관계형 모델링

- **단방향 관계 저장**: 에지의 시작점과 도착점을 하나의 행으로 저장한다. 특정 사용자가 팔로우하는 대상을 찾으려면 인덱스로 시작점을 찾아야 한다.
- **양방향 관계 저장**: 출발점과 도착점을 번갈아 저장하고 방향을 나타내는 값을 덧붙여, 양쪽에서 관계를 조회할 수 있다.

#### 그래프 모델링

- **구조**: 데이터를 이중 연결 리스트 그래프와 노드 테이블, 관계 테이블로 표현한다. 노드 레코드에는 첫 번째 관계 ID(first_rid)가, 관계 레코드에는 출발점(src)과 도착점(dst), 그리고 각 노드의 이전과 다음 관계 ID가 저장된다.
- **노드 추가**: 새 노드를 넣으면 노드 테이블에 레코드를 추가하고 관계 테이블에 새 관계 ID를 넣으면서 기존 포인터도 함께 갱신한다.
- **저장 구조**: 모든 노드는 노드 저장소에 15바이트 레코드로 저장되고(사용 여부, 노드 ID, 첫 관계 ID, 첫 속성 ID, 레이블 저장소 등), 관계는 관계 저장소에 34바이트 레코드로 저장된다(출발 노드 ID, 도착 노드 ID, 관계 유형 포인터, 이전과 다음 관계 레코드 포인터).

## 5.13 요약

- **데이터베이스 유형**: 구조화된 데이터와 강한 무결성에 적합한 관계형(MySQL, PostgreSQL, Oracle)과, 유연성과 확장성이 뛰어난 비관계형으로 나뉜다.
- **키-값 저장소**: 일관된 해싱과 가상 노드로 확장성을, 주종과 동등 복제 모델로 가용성을, r과 w 설정으로 일관성을, 힌트 전달과 머클 트리로 장애 허용성을 확보한다.
- **비관계형 사례**: 키-값 및 문서형인 DynamoDB, 대규모 쓰기에 강한 컬럼 패밀리(카산드라, HBase), 복잡한 관계를 다루는 그래프(Neo4j)를 각각의 설계와 내부 동작까지 살펴봤다.
- 다음 장에서는 캐시의 종류와 소프트웨어 시스템 설계에서의 역할을 다룬다.
