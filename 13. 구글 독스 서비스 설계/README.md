# 13. 구글 독스 서비스 설계

구글 독스는 여러 사용자가 온라인에서 문서를 동시에 작성하고 편집하며 공유하는 실시간 협업 서비스다. 동시 편집을 충돌 없이 처리하면서 방대한 사용자 생성 콘텐츠를 안정적으로 다루는 것이 핵심 도전이다. 이 장은 요구 사항과 데이터 모델, 규모 산정, 고수준 설계를 거쳐 문서, 협업, 접근 제어 세 핵심 서비스의 세부 설계를 다룬다.

## 13.1 기능적 요구 사항

- **사용자 등록과 인증**: 이름과 이메일, 비밀번호로 계정을 만들고 인증 정보를 안전하게 저장하며 세션을 관리한다.
- **문서 생성과 편집, 삭제**: 다양한 서식을 갖춘 리치 텍스트 편집기로 문서를 공동 작성하고, 소유하거나 권한을 부여받은 문서를 삭제한다.
- **실시간 협업과 동기화**: 여러 사용자가 같은 문서를 동시에 편집하고 변경 사항이 실시간으로 동기화되며, 다른 사람의 참여 여부와 커서 위치를 확인한다.
- **공유와 접근 권한**: 공유 링크나 권한 부여로 문서를 공유하고 보기 전용, 댓글 전용, 편집 등 접근 수준을 지원하며 소유자가 협업자와 권한을 관리한다.
- **버전 기록과 댓글**: 수정 내용을 자동 저장해 버전 기록을 관리하고 이전 버전으로 복원하며, 특정 부분에 댓글과 수정 제안을 달고 문서를 폴더로 정리해 검색한다.

## 13.2 비기능적 요구 사항

- **확장성**: 서버를 추가해 수평 확장하고 문서 서비스나 협업 서비스 같은 기능을 독립적으로 확장한다.
- **가용성과 지연 시간**: 서버 중복과 레플리카, 지리적 중복성으로 장애에도 안정성을 확보하고, 실시간 협업을 위해 최소한의 지연 시간으로 작동한다.
- **데이터 일관성과 무결성**: 여러 사람이 동시에 편집해도 변경 사항이 적절히 동기화되고 병합되도록 충돌 해결 메커니즘으로 데이터 손상을 막는다.

## 13.3 데이터 모델

- **주요 엔티티**: User, Document, Revision, CollaboratorPermission, Comment, Suggestion, Folder, FolderDocument로 구성한다.
- **관계**: 한 사용자가 여러 문서를 소유하고 한 문서가 여러 수정 기록과 댓글, 제안을 갖는 일대다 관계, 그리고 사용자와 문서를 잇는 CollaboratorPermission과 폴더와 문서를 잇는 FolderDocument로 표현하는 다대다 관계를 담는다.

## 13.4 시스템 규모 산정

- **규모 가정**: 전체 1000만 명, 1인당 문서 100개, 문서당 50KB, 문서당 수정본 10개와 협업자 5명, 댓글 20개다.
- **저장소**: 문서 50TB, 수정본 500TB, 댓글 20TB에 메타데이터를 더해 합계 약 575TB다.
- **대역폭과 처리량**: 업로드와 다운로드, 협업 동기화를 합쳐 하루 약 10.5TB이며, 초당 문서 렌더링 약 1200번, 수정 비교 약 1200번, 실시간 협업자 500만 명 기준 협업 업데이트 약 83,000번을 처리한다.

## 13.5 고수준 설계

- **진입 구조**: 클라이언트-서버 아키텍처에서 로드 밸런서가 트래픽을 분산하고 API 게이트웨이가 진입점으로 라우팅과 인증, 속도 제한을 처리한다.

#### 핵심 마이크로서비스

- **문서 서비스**: 문서 생성과 조회, 수정, 삭제를 처리하고 메타데이터와 저장소를 관리한다.
- **협업 서비스**: 동시 편집과 동기화를 지원하며 운영 변환(Operational Transformation) 알고리즘으로 충돌을 해결하고 접속 상태를 관리한다.
- **수정 기록 서비스**: 수정 이력과 버전을 관리하며 수정본 간 차이를 비교하고 병합한다.
- **접근 제어와 알림 서비스**: 접근 제어 서비스가 인증과 권한, 공유 설정을 관리하고, 알림 서비스가 문서 변경과 댓글, 협업 이벤트를 전달한다.

#### 공통 인프라

- **데이터베이스와 저장소**: 관계형 데이터베이스에 프로필과 메타데이터, 권한을 ACID로 저장하고, MongoDB 같은 비관계형에 문서 내용과 수정 이력을 담으며, S3나 구글 클라우드 스토리지에 지능형 청킹과 멀티파트 API로 대용량 파일을 저장한다.
- **캐싱과 실시간 통신**: 레디스로 메타데이터와 세션, 자주 요청하는 내용을 캐싱하고, 웹소켓 양방향 통신으로 문서 변경을 실시간 공유한다.
- **관측과 보안**: 프로메테우스와 그라파나, ELK 스택으로 지표와 로그를 모니터링하고, OAuth 인증과 해싱, 암호화, 보안 감사로 데이터를 보호한다.

## 13.6 서비스 세부 설계

#### 문서 서비스

- **API**: 문서를 다루는 `POST /documents`, `GET/PUT/DELETE /documents/{id}`와 수정 이력을 조회하는 `GET /documents/{id}/revisions`를 제공한다.
- **CRUD 흐름**: 생성은 검증 후 문서 ID를 만들어 메타데이터를 관계형 데이터베이스에, 내용을 스토리지에 저장하고 그 URL을 메타데이터에 반영한다. 조회는 메타데이터의 URL로 스토리지에서 내용을 가져오고, 수정과 삭제, 수정 이력 조회도 같은 방식으로 처리한다.
- **성능과 신뢰성**: 레디스 서버 캐싱에 더해 IndexedDB나 로컬 스토리지 같은 브라우저 캐시로 오프라인 편집과 빠른 반응, 복원력을 제공한다. 메타데이터 갱신은 트랜잭션으로 묶고, 스테이트리스 인스턴스를 여러 개 두어 로드 밸런싱하며 문서 ID 범위로 샤딩해 확장한다.

#### 협업 서비스

- **API**: 편집 모드로 전환하는 `POST /collaborate/{id}`, 실시간 통신용 `WebSocket /collaborate/{id}`, 접속 상태를 갱신하는 `POST /presence/{id}`를 제공한다.
- **협업 과정**: 편집 요청 시 권한을 확인하고 협업 세션과 초기 문서 상태를 만든 뒤 웹소켓을 설정한다. 사용자가 삽입이나 삭제, 서식 변경 이벤트를 웹소켓으로 보내면 운영 변환으로 충돌을 해결한 뒤 변환된 이벤트를 연결된 모든 클라이언트에 전파해 로컬 상태를 동기화한다.
- **운영 변환(Operational Transformation)**: 현재 문서 상태와 이전에 적용된 작업 이력을 기준으로 새로 들어오는 작업을 변환해, 작업 순서와 관계없이 모든 사용자가 동일한 최종 문서 상태를 유지하는 기법이다. 서버가 문서 상태와 각 클라이언트의 작업 이력을 관리하며 변환한 작업을 반영하고 전파한다.
- **접속 상태와 확장성**: presence 엔드포인트로 접속 상태를 갱신하고 문서별 해시 맵으로 협업자 목록을 관리하며 비활성 클라이언트를 감지한다. 스테이트리스 배포에 레디스 분산 캐시로 문서 상태와 접속 정보를 공유하고, 카프카로 협업 이벤트를 전달해 웹소켓 관리와 이벤트 처리를 분리한다.

#### 접근 제어 서비스

- **API**: 로그인과 로그아웃 `POST /auth/login|logout`, 권한 조회와 부여 `GET/POST /permissions/{id}`, 권한 철회 `DELETE /permissions/{id}/{userId}`를 제공한다.
- **인증**: 자격 증명을 데이터베이스와 대조해 확인하고 user_id와 역할을 담은 JWT 액세스 토큰을 발급하며, 이후 클라이언트는 모든 요청 헤더에 토큰을 포함한다.
- **인가**: 요청의 토큰 무결성을 검증하고 user_id와 역할을 추출한 뒤, 권한 데이터베이스에서 해당 문서에 대한 권한을 조회해 작업 수행 권한이 있으면 해당 서비스로 전달하고 없으면 거부한다.
- **권한 관리와 데이터베이스 설계**: 요청자의 권한을 검증한 뒤 권한 데이터베이스에 항목을 추가하거나 수정, 삭제한다. User, AccessToken, Permission, Document 테이블로 구성하며, Permission 테이블이 사용자와 문서를 잇는 중간 테이블(junction table) 역할을 하고 AccessToken 테이블이 활성 세션과 만료 시간을 관리한다.

## 13.7 기타 검토 사항 및 모범 사례

- **성능 최적화**: 다층 캐싱과 CDN, 데이터베이스 쿼리와 인덱스 최적화, 필요한 순간에 불러오는 레이지 로딩(lazy loading), 페이지네이션으로 응답 속도를 높인다.
- **데이터 일관성과 동시성**: 버전 번호나 타임스탬프를 쓰는 낙관적 동시성 제어(optimistic concurrency control)로 충돌을 감지하고 해결한다. 이는 매번 락을 걸지 않아 성능이 좋지만 충돌 시 해결이 필요한 방식이며, 협업 편집에서 주로 쓴다. 분산 잠금과 최종 일관성도 상황에 맞게 적용한다.
- **장애 내성과 확장성**: 일정 횟수 이상 실패하면 호출을 차단했다가 복구 후 재시도하는 서킷 브레이커(circuit breaker) 패턴과 재시도, 이중화와 복제, 백업으로 복원력을 확보하고, 자동 스케일링과 로드 밸런싱, 메시지 큐로 탄력적으로 확장한다.
- **지속적 통합과 배포**: CI/CD 파이프라인으로 빌드와 테스트, 배포를 자동화하고 도커와 쿠버네티스를 활용하며, 블루-그린 배포와 카나리 배포, 롤링 업데이트로 다운타임을 최소화한다.

## 13.8 요약

- **핵심 설계**: 문서, 협업, 수정 기록, 접근 제어 서비스를 중심으로 요구 사항과 데이터 모델, 규모 산정, 고수준 아키텍처를 다뤘다.
- **실시간 협업**: 운영 변환 알고리즘과 충돌 해결로 여러 사용자가 동시에 편집해도 문서를 일관되게 유지하고, 웹소켓과 분산 캐시로 실시간 동기화를 구현했다.
- **마무리**: 캐싱과 레이지 로딩 같은 성능 최적화와 CI/CD로 안정성과 사용자 경험을 높였다. 다음 장에서는 넷플릭스 서비스 설계를 다룬다.
