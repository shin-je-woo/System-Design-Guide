# 11. X 서비스 설계

X(트위터)는 짧은 메시지인 트윗을 공유하는 마이크로블로깅(microblogging) 서비스로, 매일 수십억 개의 트윗을 다룬다. 이런 서비스를 설계하려면 확장성과 신뢰성, 사용자 경험을 모두 만족해야 한다. 이 장은 요구 사항과 데이터 모델, 규모 산정, 고수준 설계를 거쳐 트윗, 사용자, 타임라인, 검색 네 핵심 서비스의 세부 설계를 다룬다.

## 11.1 기능적 요구 사항

- **사용자 등록과 인증**: 이름과 이메일, 비밀번호로 계정을 만들고, 자격 증명을 안전하게 저장하며, 세션을 효율적으로 관리한다.
- **트윗 생성**: 최대 280자 메시지에 텍스트, 해시태그, 멘션, 이미지나 동영상을 첨부하고 빠르게 저장하고 불러온다.
- **팔로우와 언팔로우**: 다른 사용자를 팔로우해 타임라인에서 보고, 팔로우 그래프를 관리하며 언제든 언팔로우한다.
- **타임라인**: 팔로우한 계정의 트윗을 시간순으로 보여 주고 실시간으로 갱신한다.
- **검색과 상호 작용**: 키워드, 해시태그, 사용자 이름으로 검색하되 연관성과 인기, 최신성을 반영하고, 리트윗과 좋아요, 암호화된 다이렉트 메시지를 지원한다.

## 11.2 비기능적 요구 사항

- **확장성**: 서버를 추가해 수평 확장하고, 트윗 서비스나 타임라인 서비스 같은 개별 구성 요소를 독립적으로 확장한다.
- **가용성**: 다운타임을 최소화하고 서버와 데이터베이스, 지역 간 이중화로 장애 시에도 서비스를 유지한다.
- **신뢰성**: 백업과 레플리카로 데이터 손실을 막고, 최종 일관성이나 강한 일관성을 상황에 맞게 선택한다.
- **지연 시간**: 실시간 업데이트와 빠른 응답을 위해 캐싱과 콘텐츠 전송 네트워크로 조회 지연을 줄인다.

## 11.3 데이터 모델

- **주요 엔티티**: User, Tweet, Follow, Like, Retweet, DirectMessage로 구성하며, 한 사용자가 여러 트윗을 쓰는 일대다와 여러 사용자를 팔로우하는 다대다 관계를 담는다.
- **핵심 구조**: User는 user_id를 기본 키로 프로필을 담고, Tweet은 tweet_id를 기본 키로 작성자 user_id와 내용, 미디어 URL, 좋아요와 리트윗 수를 담는다. Follow는 follower_id와 followee_id로 관계를, Like와 Retweet은 각각 사용자와 트윗 ID를, DirectMessage는 발신자와 수신자 ID, 내용을 담는다.

## 11.4 시스템 규모 산정

- **규모 가정**: 전체 사용자 1억 명, 일간 활성 사용자 2000만 명, 1인당 하루 5트윗, 트윗당 200바이트, 트윗의 20퍼센트가 1MB 미디어 포함, 보관 5년이다.
- **저장소**: 트윗은 5년간 약 36.5TB, 미디어는 약 3650TB, 사용자는 약 100TB로 합계 약 3650TB다.
- **대역폭**: 평균 팔로워 100명 기준 트윗 전달에 하루 약 2TB, 미디어 전달에 약 20TB로 하루 약 22TB다.
- **처리와 캐시**: 초당 트윗 약 1200건, 미디어 업로드 약 240건, 타임라인 팬아웃 요청 약 12만 건이며, 캐시는 적중률 80퍼센트 기준 약 320GB다.

## 11.5 고수준 설계 탐구

- **진입 구조**: 클라이언트-서버 아키텍처에서 로드 밸런서가 트래픽을 분산하고, API 게이트웨이가 요청의 진입 지점으로 라우팅과 인증, 속도 제한을 처리한다.

<img width="643" height="734" alt="image" src="https://github.com/user-attachments/assets/fd106a9d-eb5b-441f-a3d9-d6c13091feb1" />

#### 핵심 마이크로서비스

- **트윗 서비스**: 트윗 생성과 조회, 삭제를 처리하고 미디어를 객체 저장소에 보관하며 새 트윗을 메시지 큐에 전달한다.
- **사용자 서비스**: 등록과 인증, 프로필을 관리하고 팔로우와 언팔로우 관계를 유지한다.
- **타임라인 서비스**: 팔로우한 계정의 트윗을 모아 타임라인을 만들고 캐시에 저장한다.
- **검색 서비스**: 트윗과 사용자를 인덱싱하고 연관성과 인기도로 순위를 매겨 검색 결과를 제공한다.

#### 공통 모듈

- **캐싱과 데이터베이스**: 레디스 캐싱으로 자주 조회하는 데이터의 백엔드 부하를 줄이고, 카산드라나 DynamoDB 같은 분산 데이터베이스에 샤딩과 복제로 정형 데이터를 저장한다.
- **객체 저장소와 메시지 큐**: 미디어 파일은 아마존 S3에 보관하고, 아파치 카프카로 서비스 간 비동기 통신과 결합도 완화를 처리한다.
- **실시간과 관측**: 웹소켓(WebSocket)으로 실시간 업데이트를 전달하고, 프로메테우스와 그라파나, ELK 스택으로 지표와 로그를 모니터링한다.
- **보안**: OAuth로 인증과 권한을 처리하고, 비밀번호를 해싱하며 전송과 저장 시 암호화하고 속도 제한을 적용한다.

## 11.6 트윗 서비스 설계

- **API**: 트윗을 만드는 `POST /tweets`, 조회하는 `GET /tweets/{id}`, 삭제하는 `DELETE /tweets/{id}`, 특정 사용자 트윗을 조회하는 `GET /users/{id}/tweets`를 제공한다.
- **데이터 저장소**: 데이터베이스는 트윗 ID를 파티션 키로 삼아 데이터를 고르게 분산하고 타임스탬프를 클러스터링 키로 삼아 시간순 조회를 돕는다. 미디어 파일은 객체 저장소에 고유 식별자로 저장하고 트윗 정보에 그 식별자를 참조로 담는다.

<img width="695" height="314" alt="image" src="https://github.com/user-attachments/assets/cd1db611-e6b8-4c3f-a983-0a015effd858" />

- **생성 과정**: 요청 유효성을 검사하고, 미디어가 있으면 객체 저장소에 올려 식별자를 받은 뒤, 트윗 ID를 만들어 데이터베이스에 저장하고 응답하며, 마지막에 트윗 메시지를 메시지 큐에 발행해 타임라인과 검색 서비스가 처리하게 한다.
- **조회 과정**: 인증과 권한을 확인하고 데이터베이스에서 트윗을 찾은 뒤, 미디어가 있으면 객체 저장소에서 가져와 결합해 반환한다.

#### 캐싱 전략과 삭제 정책

- **캐싱 전략**: 최근 트윗을 유지하는 시간 기반 슬라이딩 윈도우, 반응 점수로 거르는 인기도 기반, 둘을 합친 하이브리드, 머신러닝으로 인기 트윗을 예측하는 예측 기반, 영향력 있는 사용자의 최신 트윗을 담는 사용자 기반이 있다.
- **삭제 정책**: 오래 안 쓴 트윗을 지우는 LRU, 유효 기간을 두는 TTL, 조회 빈도가 낮은 것을 지우는 LFU, 크기 기반 삭제, 영향력과 작성 시점으로 정하는 우선순위 기반 삭제가 있다.
- **구현 고려**: 핫과 웜, 콜드로 나눈 다층 캐시, 재시작 대비 캐시 워밍(cache warming), 수정과 삭제에 대비한 캐시 버전 관리, 데이터 유형별 캐시 분리를 적용한다.

## 11.7 사용자 서비스 설계

- **API**: 계정 생성 `POST /users`, 프로필 조회와 수정 `GET/PUT /users/{id}`, 팔로우와 언팔로우 `POST/DELETE /users/{id}/follow`, 팔로워와 팔로잉 목록 `GET /users/{id}/followers|following`을 제공한다.
- **데이터 저장소**: 사용자 정보는 PostgreSQL이나 MySQL의 사용자 테이블에 user_id를 기본 키로 저장하고, 팔로우 관계는 팔로워 ID와 팔로잉 ID를 복합 기본 키(composite primary key)로 두어 고유성을 보장한다.

<img width="548" height="307" alt="image" src="https://github.com/user-attachments/assets/0cc9b8e3-d382-48e9-b2fd-6d7277312cc3" />

- **주요 과정**: 사용자 생성은 중복을 검증하고 user_id 생성과 비밀번호 해싱 후 저장한다. 인증은 자격 증명을 대조해 인증 토큰을 생성해 반환하고, 팔로우와 언팔로우는 토큰을 검증한 뒤 팔로우 테이블에 항목을 추가하거나 삭제한다. 팔로워와 팔로잉 조회는 팔로우 테이블에서 ID 목록을 얻어 사용자 테이블에서 프로필을 가져온다.

## 11.8 타임라인 서비스 세부 설계

- **API**: 홈 타임라인 `GET /timeline/{id}`와 멘션 타임라인 `GET /timeline/{id}/mentions`를 제공한다.
- **데이터 흐름(쓰기 시 팬아웃)**: 새 트윗이 만들어지면 트윗 서비스가 메시지 큐에 발행하고, 타임라인 서비스가 작성자의 팔로워 ID 목록을 받아 각 팔로워의 타임라인에 트윗 ID를 추가해 캐시에 저장한다. 타임라인은 사용자별 최근 트윗으로 개수나 시간을 제한한다.

<img width="723" height="302" alt="image" src="https://github.com/user-attachments/assets/3fbcac48-b6e4-45d5-aeb5-13066c45b710" />

- **조회 과정**: 토큰을 검증하고 캐시에서 타임라인을 가져오되, 없거나 불완전하면 데이터베이스에서 누락된 트윗 ID를 보충한 뒤, 트윗 서비스에서 실제 객체를 받아 타임스탬프순으로 정렬해 반환한다.
- **멘션과 푸시**: 멘션 타임라인은 새 트윗의 멘션을 확인해 멘션별로 메시지 큐에 발행하고 멘션 전용 구조에 추가한다. 새 트윗이 생기면 웹소켓으로 실시간 알림을 보내 클라이언트가 즉시 갱신한다.

## 11.9 검색 서비스 세부 설계

- **API**: 트윗을 찾는 `GET /search/tweets`와 사용자를 찾는 `GET /search/users`를 제공하며 검색어와 limit, offset을 받는다.
- **데이터 흐름과 인덱싱**: 트윗과 사용자 서비스가 메시지 큐로 데이터를 보내면, 검색 서비스가 텍스트와 해시태그, 멘션, 사용자 정보를 추출해 엘라스틱서치에 단어와 트윗 ID를 잇는 역색인(inverted index)을 만든다.

<img width="578" height="201" alt="image" src="https://github.com/user-attachments/assets/945edcab-581e-4c92-bbdb-fcd9f9f3a615" />

- **쿼리 처리**: 검색 쿼리를 분석해 엘라스틱서치 쿼리로 변환하고, 검색을 수행한 뒤 필터링과 정렬, 페이지네이션을 거쳐 반환한다.
- **관련 점수와 순위**: 단어 빈도(TF), 역문서 빈도(IDF), 특정 필드에 가중치를 주는 필드 부스팅을 종합해 연관성 점수를 계산하고 결과 순서를 정한다.

## 11.10 기타 고려 사항

- **인기 주제와 해시태그 관리**: 아파치 스톰이나 플링크 같은 실시간 처리 도구로 들어오는 트윗을 분석해 인기 주제를 빠르게 갱신하고 결과를 캐시나 데이터베이스에 저장한다.
- **속도 제한과 트래픽 조절**: 엔드포인트별 사용 패턴과 시스템 용량에 맞춰 토큰 버킷이나 리키 버킷으로 한도를 초과하는 요청을 제한한다.

## 11.11 요약

- **핵심 설계**: 트윗, 사용자, 타임라인, 검색 네 서비스를 중심으로 요구 사항과 데이터 모델, 규모 산정, 고수준 아키텍처를 다뤘다.
- **확장 기법**: 캐싱과 샤딩, 비동기 처리를 활용해 대규모 사용자와 상호 작용을 효율적으로 처리하고 응답 속도를 높였다.
- **마무리**: 이런 원칙을 지키면서 지속적으로 개선해야 안정적인 시스템을 유지할 수 있다. 다음 장에서는 인스타그램 같은 서비스 설계를 다룬다.
