# 07. 발행/구독과 분산 큐

방대한 데이터를 안정적이고 확장성 있게 처리하고 배포하려면 분산 시스템의 메시징 패턴이 필요하다. 발행/구독(publish/subscribe) 시스템과 분산 큐는 마이크로서비스 아키텍처에서 서비스 간 느슨한 결합을 가능하게 해 확장성과 안정성을 높인다.

## 7.1 분산 시스템의 발전 과정

- **발전 흐름**: 모든 구성 요소가 하나의 서비스에 밀접하게 묶인 모놀리식에서, 각 서비스가 독립적으로 분리되어 메시지로 소통하는 마이크로서비스로 발전했다.
- **분산 큐**: 여러 서버에 분산된 큐로 메시지를 저장하고 전달한다. 메시지를 보낸 순서대로 처리해야 하거나 각 메시지가 하나의 소비자만 대상으로 할 때 주로 쓴다.

#### 큐를 활용하는 이점

- **부하 관리**: 메시지 생성자(producer)와 소비자(consumer) 사이에서 완충 역할을 해, 메시지가 폭증해도 시스템이 과부하에 걸리지 않게 한다.
- **결합도 낮추기**: 생성자와 소비자가 서로의 상태를 몰라도 되므로 시스템을 모듈화하고 유지 보수하기 쉽다.
- **신뢰성과 일관성**: 소비자가 처리에 실패해도 큐가 메시지를 다시 전달해 데이터 일관성을 지킨다.

#### 분산 큐의 구성 요소

- **큐 관리자(queue manager)**: 메시지 분배를 책임지며 순서를 유지하고, 적절한 소비자에게 전달하며, 처리 실패 시 재전송을 관리한다.
- **메시지 저장소(message storage)**: 소비자가 처리하기 전까지 메시지를 보관하며, 높은 신뢰성과 빠른 읽기 및 쓰기를 갖춰야 한다.
- **로드 밸런싱과 장애 복구**: 각 소비자의 작업량과 처리 능력에 맞춰 메시지를 고르게 배분하고, 실패한 메시지를 감지해 재전달하거나 다른 경로로 보낸다.

#### 아키텍처 설계 시 고려 사항

- **메시지 순서와 전달 보장**: 순서를 엄격히 유지할지, 최소 한 번(at-least-once) 또는 정확히 한 번(exactly-once) 전달할지를 요구에 맞게 정한다.
- **데이터 영속성**: 소비자가 확인할 때까지 메시지를 보관할지, 성능을 위해 일정 손실을 허용할지 데이터 무결성과 성능 사이에서 결정한다.
- **보안과 기술 스택**: 메시지 무결성과 접근 제어로 보안을 확보하고, 언어 지원과 성능, 기존 인프라 호환성에 따라 RabbitMQ, 카프카, 아마존 SQS 중에서 고른다.
- **장애 허용성**: 재시도 메커니즘과, 처리 불가능한 메시지를 관리하는 데드 레터 큐(dead letter queue)로 데이터 손실을 최소화한다.

## 7.2 발행/구독 시스템 설계

- **발행/구독 모델**: 생성자(발행자)가 특정 토픽에 메시지를 발행하면 소비자(구독자)가 구독한 토픽의 메시지를 받는 구조다. 여러 소비자에게 동시에 정보를 전달해 실시간 데이터 처리에 효과적이다.
- **토픽(topic)**: 생성자가 발행하고 소비자가 받도록 설정된 카테고리나 채널로, 연관된 메시지를 논리적으로 묶는다.

#### 주요 특징

- **낮은 결합도**: 생성자가 소비자를 알 필요가 없어 유연성과 확장성이 크게 향상된다.
- **확장성과 유연성**: 대량 메시지를 여러 소비자에게 효율적으로 분배하며, 소비자는 실시간 분석부터 이벤트 기반 처리까지 다양하게 활용한다.
- **설계 요소**: 토픽을 생성하고 삭제하는 토픽 관리, 메시지를 적절한 소비자에게 보내는 라우팅, 구독 상태를 다루는 소비자 관리, 전달 수준을 정하는 서비스 품질(QoS), 확장성과 로드 밸런싱을 신중히 설계한다.

#### 설계 시 확장성 요소

- **수평 확장과 수직 확장**: 수평 확장은 장비를 추가해 유연성과 안정성이 뛰어나고, 수직 확장은 기존 장비에 자원을 더해 단기적으로 간편하지만 장기적으로는 덜 유연하다.
- **동적 로드 밸런싱**: 메시지 브로커가 여러 구독자 사이에 부하를 실시간으로 분산해, 발행자와 구독자는 자기 역할에만 집중하고 특정 노드의 병목을 막는다.
- **토픽 파티셔닝**: 하나의 토픽을 여러 파티션으로 나눠 메시지 부하를 시스템 전체에 분산한다. 생산과 소비가 독립적이라 발행자나 구독자를 추가하거나 제거해도 서로 영향을 주지 않아 성능 최적화의 핵심이 된다.

#### 설계 시 신뢰성 요소

- **메시지 전달 보장**: 최대 한 번, 최소 한 번, 정확히 한 번 중 어떤 수준으로 전달할지 정해 데이터 손실과 중복 처리를 관리한다.
- **장애 허용성**: 데이터를 여러 노드에 복제하고 재시도 메커니즘을 둬, 일부 구성 요소에 문제가 생겨도 서비스가 중단되지 않게 한다.
- **메시지 순서**: 순서가 중요한 애플리케이션에서는 시간적 순서를 유지하도록 설계하며, 여러 경로를 거치는 분산 환경에서는 특히 까다롭다.

#### 기본 구축 단계

- 확장성과 신뢰성을 갖춘 플랫폼(카프카, RabbitMQ, 구글 발행/구독)과 언어를 고르고, 토픽과 인프라를 설정한 뒤, 오류 처리와 재시도를 포함한 생성자와 소비자를 구현하고, 여러 상황에서 테스트하며 로드 밸런싱과 라우팅을 조정해 최적화한다.

## 7.3 카프카

- **정의**: 아파치 카프카는 대용량 실시간 데이터 피드를 처리하는 분산 스트리밍 플랫폼으로, 내구성과 속도, 확장성을 갖추고 발행/구독과 큐 기반 메시징을 모두 구현한다.

#### 핵심 개념

- **토픽과 생성자, 소비자**: 레코드가 토픽 카테고리로 분류되며, 생성자는 토픽에 데이터를 보내고 소비자는 원하는 토픽을 골라 읽는다. 생성자와 소비자를 독립적으로 확장할 수 있다.
- **브로커(broker)**: 카프카 클러스터를 이루는 서버로, 생성자가 보낸 데이터를 저장하고 소비자를 관리하며 어디까지 읽었는지 추적한다.
- **파티션과 복제**: 각 토픽을 여러 파티션으로 나누고 데이터를 여러 브로커에 복제해 장애에 대비하고 처리량을 높인다.
- **오프셋(offset)**: 소비자마다 파티션에서 읽은 위치를 관리해 모든 메시지를 한 번씩 순서대로, 중복이나 누락 없이 읽도록 보장한다.

<img width="661" height="439" alt="image" src="https://github.com/user-attachments/assets/1624fdd0-bb44-410a-bf5c-e29f065289aa" />

- **주키퍼의 역할과 변화**: 주키퍼가 각 파티션의 리더를 결정하고 브로커 상태를 추적한다. 다만 카프카 2.8 버전부터 주키퍼 의존이 크게 줄어, 클러스터 메타데이터 관리와 브로커 조율을 카프카 컨트롤러 브로커와 카프카 래프트(KRaft) 합의 프로토콜이 담당한다.

#### 분산 시스템에서 카프카의 중요성

- **이벤트 스트리밍 플랫폼**: 단순 메시징을 넘어 대규모 데이터를 낮은 지연으로 처리한다. 배포는 장애 허용성을 위한 다중 브로커 클러스터 설정, 파티션 수와 복제 계수를 정하는 토픽 생성, 직렬화와 오프셋 관리를 다루는 생성자와 소비자 구현, 클러스터 모니터링과 성능 튜닝 단계를 거친다.

## 7.4 카프카 스트림

- **정의**: 아파치 카프카 위에서 데이터를 실시간으로 처리하고 분석하는 애플리케이션을 만드는 도구다. 별도 스트림 처리 프레임워크 없이 카프카 내에서 작업하며, 고수준 DSL과 저수준 Processor API를 제공한다.

#### 주요 특징

- **카프카 완전 통합**: 카프카 토픽에서 자연스럽게 읽고 쓰며, 파티션과 복제 기능을 활용해 장애 허용성과 확장성을 높인다.
- **두 가지 처리 방식**: 고수준 DSL(Domain-Specific Language)은 map, filter, join, aggregate 연산을 선언적으로 조합하게 하고, 저수준 Processor API는 처리 구조(토폴로지)와 상태를 세밀하게 제어하게 한다.
- **상태 기반 처리**: 시간이 지나도 애플리케이션 상태를 유지하고 갱신하도록 상태 저장소를 제공한다.
- **정확히 한 번 처리(exactly-once processing)**: 카프카의 트랜잭션 기능으로 실패 시에도 중복이나 누락 없이 레코드를 한 번만 처리한다.
- **확장성과 장애 허용성**: 인스턴스를 추가하면 카프카가 파티션을 나눠 작업을 분배하고, 복제와 장애 대응 메커니즘으로 일부 노드 문제에도 안정적으로 동작한다.
- **스트림 처리 토폴로지**: 애플리케이션을 스트림 프로세서(노드)와 스트림(에지)으로 이뤄진 그래프로 정의하며, 입력 토픽(소스), 프로세서, 출력 토픽(싱크)으로 파이프라인을 구성한다.
- **활용 사례**: 실시간 데이터 분석, 이벤트 기반 아키텍처, 데이터 보강과 변환, 부정행위 감지, 스트리밍 ETL에 쓴다.

## 7.5 키네시스

- **정의**: 키네시스는 AWS가 제공하는 클라우드 기반 완전 관리형 서비스로, 대규모 데이터 스트림을 아주 짧은 지연으로 실시간 처리한다. 실시간 분석과 로그, 이벤트 데이터 처리, 대규모 애플리케이션 모니터링에 적합하다.

#### 구성 요소

- **키네시스 데이터 스트림**: 서비스의 중심으로, 여러 소스에서 오는 대규모 데이터를 실시간으로 수집하고 처리한다.
- **키네시스 데이터 파이어호스**: 스트림 데이터를 받아 필요하면 변환한 뒤 아마존 S3, Redshift, 엘라스틱서치, Splunk 같은 저장소에 자동으로 적재한다.
- **키네시스 데이터 애널리틱스**: 표준 SQL 쿼리로 스트리밍 데이터를 직접 처리해, 배치나 별도 내보내기 없이 들어오는 데이터를 즉시 분석한다.

## 7.6 요약

- **분산 큐**: 확장성과 안정성, 메시지 무결성을 보장하며 구성 요소 간 부하를 완충한다.
- **발행/구독 시스템**: 생성자와 소비자의 결합도를 낮춰 시스템 유연성을 높이고, 토픽 파티셔닝과 전달 보장으로 확장성과 신뢰성을 확보한다.
- **플랫폼**: 대용량 실시간 스트리밍에 강한 아파치 카프카와 그 위의 카프카 스트림, 클라우드 완전 관리형인 아마존 키네시스를 다뤘다.
