# 10. 근접 서비스 설계

근접 서비스(proximity service)는 사용자의 위치 데이터를 기반으로 주변 대상을 찾아 주는 서비스다. 위치 기반 마케팅부터 주변 식당 찾기까지 여러 산업에서 쓰인다. 이 장은 내 주변 음식점을 찾고 주문하는 서비스를 예로 삼아 요구 사항 정의부터 위치 기반 검색 알고리즘, 아키텍처까지 설계한다.

## 10.1 실제 활용 사례와 요구 사항

#### 활용 사례

- 가까운 드라이버를 매칭하고 탄력 요금을 적용하는 승차 공유(우버, 리프트), 위치 기반 추천과 체크인을 제공하는 지역 검색(옐프, 포스퀘어), 배달 경로를 최적화하고 실시간 추적하는 음식 배달(도어대시, 그럽허브), 주변 사람과 연결하는 소셜과 데이팅(틴더, 범블), 실시간 경로를 안내하는 내비게이션(구글 맵, 웨이즈), 활동을 기록하는 피트니스(스트라바, 핏빗)에 쓴다.

#### 기능 요구 사항

- 사용자가 자신의 위치를 기준으로 주변 음식점을 검색하고, 음식점을 선택해 주문할 수 있어야 한다.

#### 비기능 요구 사항

- **가용성과 확장성**: 항상 높은 가용성을 유지하고, 사용자 1억 명과 요청 폭주를 감당해야 한다.
- **지연 시간**: 음식점 정보는 자주 바뀌지 않아 쓰기 요청이 적다고 가정하며, 읽기 요청의 지연 시간은 200밀리초 이내여야 한다.
- **일관성과 신뢰성**: 음식점 정보 갱신에 최종 일관성을 허용하고, 장애나 폭주 상황에서도 올바르게 작동해야 한다.

## 10.2 API 설계

- **`GET /restaurants/search?lat=&long=&distance=`**: 위치와 반경으로 주변 음식점 목록을 조회한다.
- **`POST /orders/place`**: 사용자, 음식점, 항목, 결제 수단을 담아 주문한다.

## 10.3 계산으로 문제 규모 파악

- **QPS 추산**: 사용자 1억 명 중 일간 활성 사용자(DAU)가 10퍼센트인 1000만 명이고, 주문이 점심과 저녁 6시간에 몰린다고 가정하면 약 1200 QPS다. 폭주 시 5배인 약 6000 QPS이고, 검색은 주문의 5배라 약 6000 QPS다.
- **데이터 규모**: 전 세계 음식점 1000만 개 중 100만 개가 주문 가능한 상태이며 데이터는 자주 바뀌지 않는다.
- **결론**: 높은 QPS와 트래픽 폭주를 감당할 확장성과 유연성이 필요하다.

## 10.4 시스템 설계

- **핵심 엔티티**: 고객, 음식점, 주문이며, 고객 CRUD 서비스와 음식점 검색 서비스, 주문 관리 서비스가 각각을 담당한다.

핵심 과제는 사용자 위치(위도 lat, 경도 long)를 기준으로 특정 반경 내 음식점을 찾는 것이다. 세 가지 방법을 검토한다.

- **방법 1, 위치 값 SQL 쿼리**: 음식점의 위도와 경도를 관계형 데이터베이스에 저장하고 사용자 좌표 기준 범위 조건으로 검색한다. 테이블 전체를 스캔해 매우 비효율적이고, 인덱스는 한 번에 하나만 쓸 수 있어 위도와 경도 두 값을 동시에 좁히지 못한다.

#### 방법 2, 쿼드 트리

- **원리**: 쿼드 트리(quadtree)는 각 노드가 자식 넷을 가지는 트리다. 지도를 구역으로 나누고 각 구역의 음식점 수가 임계 값(예: 500) 이하가 될 때까지 세분화하며, 리프 노드에는 음식점 ID 목록을, 중간 노드에는 해당 영역의 위도와 경도 최소값과 최대값을 저장한다.
- **검색**: 루트에서 시작해 사용자 위치가 포함되는 구역을 따라 DFS(깊이 우선 탐색)로 리프까지 내려간 뒤, 실제 거리를 계산해 반경 안의 음식점만 추린다. 결과가 부족하면 부모 노드로 올라가 형제 노드를 추가 탐색한다.
- **장단점**: 메모리에서 처리해 빠른 것이 장점이고, 데이터가 자주 바뀌면 트리 수정이 번거로운 것이 단점이다. 음식점 데이터는 자주 바뀌지 않아 이 단점은 감수할 수 있다.

#### 방법 3, 지오해시

- **원리**: 지오해시(geohash)는 위도와 경도를 짧은 문자열로 변환하는 방식이다. 지도를 사각형 넷으로 나눠 00, 01, 10, 11 라벨을 붙이고, 이를 재귀적으로 이어 붙여 세분화한다. 쿼드 트리와 달리 임계 값 없이 모든 영역을 균등하게 나눈다.
- **정밀도**: 문자 수가 길수록 더 작은 영역을 나타낸다. 4자리는 약 40킬로미터 사방(구 단위), 6자리는 약 1.2킬로미터 사방(거리 단위)이다.
- **저장과 검색**: 지오해시 접두어와 그 영역의 음식점 ID 목록을 관계형 테이블에 저장하고, `LIKE 'wydm9yrg%'`처럼 접두어로 시작하는 행을 조회해 주변 음식점을 찾는다.

#### 솔루션 선택

- **쿼드 트리 채택**: 단순 관계형 방식은 전체 스캔이라 부적합하다. 음식점이 적은 지역에서 지오해시는 빈 구역까지 균등하게 만들어 공간을 낭비하지만, 쿼드 트리는 임계 값 이하면 세분화하지 않고 메모리에서 빠르게 처리해 더 효율적이다. 장애 시 트리를 재구축해야 하는 단점은 음식점 데이터가 자주 바뀌지 않아 감수할 수 있으며, 음식점이 생기거나 닫힐 때 동기 업데이트로 채운다.
- **쓰기 흐름**: 고객 관련 요청은 로드 밸런서를 거쳐 고객 CRUD 서비스가 고객 데이터베이스에 반영한다. 주문 요청은 주문 관리 서비스가 고객 정보를 확인하고 음식점 데이터베이스에서 메뉴를 불러온 뒤, 결제 서비스를 호출하고 주문 데이터베이스에 저장한다.
- **읽기 흐름**: 주변 검색 요청은 로드 밸런서를 거쳐 음식점 검색 서비스가 사용자 위치로 쿼드 트리를 루트에서 리프까지 탐색해 가까운 음식점 목록을 반환한다.

## 10.5 요구 사항 검토

- **기능 요구 사항**: 위치 기반 주변 음식점 검색과 주문 기능을 모두 충족한다.
- **가용성과 확장성**: 각 서비스를 여러 인스턴스로 운영해 일부가 중단돼도 트래픽을 처리하고, 병목 없이 수평 확장한다.
- **지연 시간과 일관성**: 쿼드 트리 검색으로 읽기 지연을 200밀리초 이내로 유지하고, 음식점 데이터가 자주 바뀌지 않아 최종 일관성으로 충분하다.
- **신뢰성**: 다중 인스턴스와 데이터 내구성, 장애 허용성으로 장애나 폭주 상황에서도 안정적으로 작동한다.

## 10.6 요약

- **설계 흐름**: 승차 공유와 지역 검색, 음식 배달 등 활용 사례로 근접 서비스의 쓰임을 파악하고, 요구 사항을 정리한 뒤 QPS와 데이터 규모를 계산했다.
- **핵심 해결**: 주변 음식점을 찾는 핵심 과제를 SQL 쿼리, 쿼드 트리, 지오해시로 검토하고, 메모리에서 빠르며 업데이트가 드문 경우에 효율적인 쿼드 트리를 채택했다.
- **마무리**: 이를 반영한 고수준 아키텍처로 모든 요구 사항을 충족했다. 다음 장에서는 X(트위터)의 시스템 설계를 다룬다.
