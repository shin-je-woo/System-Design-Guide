# 09. URL 단축 서비스 설계

URL 단축 서비스는 긴 URL을 짧은 링크로 만들어 주는 서비스다. 겉보기에는 단순하지만 링크의 고유성과 안정성을 지키는 알고리즘 선택, 확장성, 일관성 등 여러 요소가 얽혀 있다. 이 장은 요구 사항 정의부터 규모 계산, 시스템 설계와 요구 사항 검토까지 실전 설계 과정을 따라간다.

## 9.1 실제 활용 사례와 요구 사항

#### 활용 사례

- 글자 수 제한이 있고 클릭 지표를 추적하는 소셜 미디어 공유, 클릭률을 추적하는 제휴 마케팅과 이메일 마케팅, 스캔이 쉬운 QR 코드, 기억하기 쉬운 인쇄 매체 캠페인, 사내 자료 공유, 동적 링크를 쓰는 모바일 앱, 자체 도메인으로 브랜드를 강화하는 커스터마이징에 쓴다.

#### 기능 요구 사항

- **핵심**: 긴 URL을 입력받아 단축 URL을 반환하고, 단축 URL을 입력받아 원본 URL을 반환하며, 단축 URL은 고유하고 길이가 일정해야 한다.
- **확장**: URL 유효성 검사, 맞춤형 URL 생성, 마지막 사용 후 6개월 만료, 오류 처리, URL 수정과 매핑 삭제, 활용도 분석, 사용자 계정 관리를 추가로 고려한다.

#### 비기능 요구 사항

- **가용성과 확장성**: 항상 안정적으로 동작하고, 사용자 1억 명 이상과 갑작스러운 요청 폭주를 감당해야 한다.
- **응답 속도와 일관성**: 읽기와 쓰기를 지연 없이 처리하고, 같은 단축 URL은 같은 원본을, 같은 긴 URL은 같은 단축 URL을 반환해야 한다.
- **내구성과 신뢰성**: 생성된 데이터는 장애 상황에서도 유실되지 않아야 하고, 요청 폭주나 문제 상황에서도 올바르게 작동해야 한다.

## 9.2 API 설계

- **`POST /shorturl`**: 긴 URL을 입력받아 새 단축 URL을 생성한다. `getShortUrl(user_id, long_url)`.
- **`GET /shorturls/{shorturl}`**: 단축 URL에 해당하는 원본 URL을 반환한다. `getLongUrl(short_url)`.

## 9.3 계산으로 문제 규모 파악

- **문자 집합**: 단축 URL에 a부터 z, A부터 Z, 0부터 9까지 62개 문자를 쓴다(Base62).
- **규모 가정**: 전체 사용자 10억 명 중 10퍼센트인 1억 명이 하루 1억 건을 생성하고, 이를 10년간 저장하면 총 3650억 개의 URL이 된다.
- **단축 URL 길이**: 여섯 글자는 62의 6제곱으로 약 500억 개라 부족하고, 일곱 글자는 62의 7제곱으로 약 3.5조 개라 충분하다. 따라서 최소 7자리가 필요하다.
- **저장 공간**: 한 레코드가 단축 URL, 원본 URL, 생성 시각, 수정 시각, 생성자를 합쳐 약 1060바이트라 1500바이트로 반올림하면, 3650억 개에 약 500TB가 들고 레플리카 세 개를 두면 약 1.5PB가 된다.
- **초당 요청 수(RPS)**: 하루 1억 건의 쓰기는 약 1000 RPS이고, 읽기는 보통 쓰기의 100배라 약 100,000 RPS다. 이 규모를 감당하려면 서버가 여러 대 필요하다.

## 9.4 시스템 설계

핵심 문제는 겹치지 않는 고유한 단축 URL을 효율적으로 생성하는 방법이다. 네 가지 방법을 검토한다.

- **방법 1, 무작위 생성**: 무작위로 단축 URL을 만든 뒤 데이터베이스에 이미 있는지 확인하고, 중복이면 재생성한다. 중복 확인을 위한 조회로 예측할 수 없는 지연이 생기고, 두 요청이 동시에 같은 단축 URL을 만들면 한쪽이 다른 쪽 데이터를 덮어쓰는 동시성 충돌이 발생한다. `putIfAbsent`나 저장 후 검증으로 완화할 수 있지만 쓰기마다 읽기가 더해져 비효율적이다.
- **방법 2, MD5 해시**: 긴 URL을 MD5(128비트)로 해싱한 뒤 42비트만 취해 7자리 Base62로 변환한다. 같은 URL이 같은 단축 URL을 만들어 중복 저장을 막는 장점이 있지만, 전체 비트 중 일부만 써서 충돌 확률이 크게 오른다. 비트를 늘리면 충돌은 줄어도 URL이 길어져 핵심 장점을 해친다.
- **방법 3, 카운터 방식**: 숫자를 1씩 증가시켜 고유 값을 만들어 충돌이 없다. 단일 서버가 카운터를 관리하면 단일 장애 지점(SPOF)이 되고, 여러 서버로 나눠 호스트 ID(6비트)와 시간, 카운터를 조합하면 호스트가 64대로 제한되며 1밀리초에 요청이 16개를 넘으면 충돌한다.

#### 방법 4, 분산 카운터 방식(채택).

- **원리**: 전체 시퀀스 약 3.5조 개를 100만 단위 범위로 나눠 약 350만 개의 범위를 만든다. 범위 할당 서버(range server)가 각 카운터 서버에 범위를 할당하고, 각 카운터 서버는 자기 범위 안에서 숫자를 증가시켜 서버 간에도 중복 없는 값을 만든다.
- **문자열 변환**: 이렇게 만든 고유 숫자를 Base62로 변환해 7자리 문자열로 만든다.
- **예외 처리**: 범위를 다 쓰면 새 범위를 요청하고, 카운터 서버가 다운되면 그 범위(100만 개)만 손실되어 전체 350만 개 중 하나라 감당할 수 있다. 범위 전체를 잃지 않도록 카운터 값을 주기적으로 기록해 장애 시 마지막 저장값에서 재시작하고, 범위 할당 서버의 단일 장애 지점 문제는 읽기와 쓰기가 적으므로 주키퍼 같은 고가용 서비스로 해결한다.

#### 적절한 데이터베이스

- **레디스**: 저장할 데이터가 단축 URL과 원본 URL의 키-값 매핑이라, 빠르고 확장성이 뛰어나며 내구성과 장애 허용성을 갖춘 레디스가 적합하다.

- **쓰기 흐름**: 클라이언트가 생성 API를 호출하면 로드 밸런서가 카운터 서버로 보내고, 카운터 서버가 값을 하나 늘려 7자리 문자열로 변환한 뒤 레디스에 매핑을 저장한다.
- **읽기 흐름**: 클라이언트가 조회 API를 호출하면 로드 밸런서가 읽기 서버로 보내고, 읽기 서버가 캐시를 먼저 확인해 있으면 바로 반환하고 없으면 레디스에서 원본 URL을 가져와 전달한다.

## 9.5 요구 사항 검토

- **기능 요구 사항**: 긴 URL과 단축 URL의 양방향 변환을 지원하고, 생성된 단축 URL은 고유하며 일곱 글자로 길이가 일정해 세 핵심 요구를 모두 충족한다.
- **가용성과 확장성**: 수평 확장 구조에 단일 장애 지점이 없어 항상 요청을 처리하고, 카운터 서버와 읽기 서버가 로드 밸런서 뒤에 있어 서버 추가만으로 확장한다.
- **지연 시간**: 쓰기는 복잡한 계산이나 조회 없이 처리하고 카운터와 URL을 미리 생성해 두면 더 빨라지며, 읽기는 인 메모리 데이터베이스인 레디스에 LRU 캐싱을 더해 성능을 높인다.
- **일관성과 내구성**: 하나의 단축 URL이 데이터베이스의 단일 항목만 저장해 일관성이 높고, 내구성을 갖춘 레디스가 데이터 유실을 막는다.

## 9.6 요약

- **설계 흐름**: 활용 사례로 필요성과 규모를 파악하고, 기능과 비기능 요구 사항을 정리한 뒤, Base62 문자 수와 저장 규모, RPS를 계산해 스케일을 이해했다.
- **핵심 해결**: 고유한 단축 URL을 만드는 무작위 생성, MD5 해시, 카운터, 분산 카운터 네 방법을 비교해 문제점을 짚고, 가장 견고한 분산 카운터 방식을 채택했다.
- **마무리**: 전체 설계를 아키텍처 다이어그램으로 정리하고 요구 사항을 다시 점검했다. 다음 장에서는 우버나 옐프 같은 서비스의 근접 서비스 설계를 다룬다.
