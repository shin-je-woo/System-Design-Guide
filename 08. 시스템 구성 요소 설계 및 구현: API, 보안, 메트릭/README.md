# 08. 시스템 구성 요소 설계 및 구현: API, 보안, 메트릭

시스템 구성 요소를 어떻게 설계하고 구현하느냐가 시스템의 효율성과 안정성, 확장성을 좌우한다. 이 장은 REST와 gRPC를 중심으로 한 API 설계, API 보안, 로깅, 메트릭, 알림, 트레이싱을 다룬다.

## 8.1 REST API

- **정의**: REST(Representational State Transfer)는 표준 HTTP 메서드를 사용해 네트워크 애플리케이션을 설계하는 아키텍처 스타일이다. 구현이 단순하고 직관적이라 널리 쓰인다.
- **설계 원칙**: 클라이언트가 접근하는 리소스를 URI로 식별하고, GET, POST, PUT, DELETE로 처리하며, 이는 데이터베이스의 CRUD 작업과 역할이 비슷하다.
- **무상태성(statelessness)**: 요청을 처리하는 데 필요한 모든 정보를 요청 안에 포함해야 한다. 서버가 요청 간 상태를 기억할 필요가 없어 동작이 안정적이고 예측 가능하다.
- **활용과 장단점**: 공개 API와 CRUD 기반 작업에 적합하고 HTTP에 익숙한 개발자에게 직관적이다. 다만 여러 요청을 한꺼번에 처리하는 복잡한 작업에 비효율적이고, JSON을 쓰므로 데이터가 많아지면 페이로드가 커진다.

## 8.2 gRPC API

- **정의**: gRPC(Google Remote Procedure Call)는 HTTP/2를 기반으로 원격 프로시저 호출을 실행하는 고성능 오픈 소스 프레임워크다. 데이터 중심인 REST와 달리 함수 중심으로 설계되었다.
- **설계 원칙**: 인터페이스 정의 언어로 프로토콜 버퍼(protobuf)를 쓰며, 이는 언어와 플랫폼에 구애받지 않고 JSON보다 효율적이고 빠르다. `.proto` 파일에 서비스를 정의하면 여러 언어의 클라이언트와 서버 코드(스텁)를 자동 생성하고, 정의가 바뀌어도 자동 반영된다.
- **활용과 장단점**: 마이크로서비스 간 빠르고 빈번한 통신과 양방향 스트리밍 실시간 애플리케이션에 적합하다. 페이로드와 속도가 우수하지만, 바이너리 형식과 HTTP/2를 요구해 설정과 디버깅이 복잡하고 통신 방식 변경 시 재정의와 배포에 시간이 더 걸린다.

## 8.3 REST와 gRPC 비교

- **성능**: gRPC가 HTTP/2와 프로토콜 버퍼를 써서 더 우수하다. HTTP/2는 단일 TCP 연결로 여러 요청을 동시에 처리하고, 프로토콜 버퍼는 JSON보다 작은 데이터를 전송한다.
- **사용 편의성**: REST는 HTTP에 익숙하면 간단하고 curl이나 포스트맨으로 쉽게 테스트한다. gRPC는 바이너리 형식이라 특정 도구가 필요하다.
- **호환성**: REST는 HTTP 기반이라 거의 모든 장치에서 쓸 수 있다. gRPC는 HTTP/2가 필요하고 웹 브라우저에서 직접 쓸 수 없다.
- **스트리밍과 활용**: gRPC는 양방향 스트리밍을 지원하고 REST는 요청과 응답만 주고받는다. REST는 공개 API와 CRUD, 폭넓은 호환성이 필요할 때, gRPC는 서비스 간 고성능 통신과 실시간 애플리케이션에 적합하다.

## 8.4 API 보안

- **인증과 인가**: 인증(authentication)은 "사용자가 누구인가"에 답하고, 인가(authorization)는 "이 작업을 해도 되는가"에 답한다.

#### 인증 방법

- **API 키**: 클라이언트가 HTTP 요청 헤더에 키를 담아 보내는 간단한 방법이다. 키가 쉽게 탈취되고 세밀한 권한 제어가 어려워 보안성이 낮다.
- **OAuth**: 사용자가 계정 정보를 직접 제공하지 않고도 한 사이트에서 다른 사이트의 리소스에 제한적 접근 권한을 부여하는 방식이다. OAuth 2.0이 다양한 환경에 맞춘 인증 절차를 제공한다.
- **JWT(JSON Web Token)**: 두 시스템 간에 정보를 안전하게 주고받는 간결한 방법이다. JSON 클레임을 JWS 서명 구조로 담아 무결성을 확인하며, 크기가 작아 URL 전송에 적합하다.

#### 인가 방법

- **역할 기반 접근 제어(RBAC)**: 권한을 개별 사용자가 아니라 역할에 할당하고 사용자를 역할에 연결한다. 역할만 관리하면 되어 관리가 간편하다.
- **속성 기반 접근 제어(ABAC)**: 사용자, 리소스, 환경 같은 속성을 조합해 권한을 정의한다. RBAC보다 세밀하지만 구현이 더 복잡하다.
- **보안 통신**: 클라이언트와 서버 간 통신을 암호화하는 HTTPS를 기본으로 쓰고, 새 취약점과 표준 발전에 맞춰 TLS 설정을 최신으로 유지한다.
- **요청 속도 제한**: 특정 시간에 보낼 수 있는 요청 수를 제한해 API 남용과 DoS 공격을 막는다. 알고리즘으로 요청마다 토큰을 소모하는 토큰 버킷(token bucket), 일정 속도로 요청이 새어 나가는 누수 버킷(leaky bucket), 시간 창 안의 요청 수를 추적하는 슬라이딩 윈도우(sliding window)가 있다.

## 8.5 분산 시스템 로깅

- **로깅**: 시스템에서 발생하는 이벤트를 기록해 내부 동작을 파악하고 문제를 추적한다. 분산 시스템에서는 여러 서비스의 로그를 종합 분석해 전반의 동작 상태를 파악한다.
- **중앙 집중형 로깅(centralized logging)**: 각 서비스가 생성한 로그를 한 저장소에 모은다. 검색과 분석이 쉬운 접근성, 타임스탬프나 식별자로 흐름을 잇는 상관관계 분석, 규제 준수를 위한 장기 보관이 장점이다.
- **대표 아키텍처**: 로그스태시가 로그를 수집하고 파싱하고 변환하며, 엘라스틱서치가 저장하고 인덱싱하고 검색하며, 키바나가 시각화와 분석을 맡는다.

- **로그 항목 필수 정보**: 발생 시각, 로그를 생성한 서비스 이름, 심각도(INFO, WARNING, ERROR), 이벤트 메시지, 사용자 ID나 트랜잭션 ID 같은 추가 정보를 담는다.
- **오픈 소스**: 엘라스틱 스택의 로그스태시, 다재다능한 수집기 Fluentd, 개방형 표준 기반의 Graylog가 있다.
- **모범 사례**: 모든 서비스가 일관된 로그 형식을 쓰고, 사용자 ID 같은 컨텍스트 정보를 포함하며, 예외에 스택 트레이스를 남기고, 상황에 맞는 로그 레벨을 설정하며, 로그를 주기적으로 순환하고 아카이빙한다.

## 8.6 분산 시스템에서 메트릭

- **메트릭**: 특정 시간 간격 동안 측정한 데이터를 수치로 표현한 것으로, 시스템 성능과 상태를 정량적으로 평가한다. 서비스 수준 목표(SLO) 충족 여부와 성능 병목을 파악하는 데 쓴다.
- **종류**: CPU와 메모리, 디스크와 네트워크 입출력을 보는 시스템 메트릭, 요청 속도와 오류 비율, 응답 시간을 보는 애플리케이션 메트릭, 가입 수나 주문 건수처럼 비즈니스 영향을 보는 비즈니스 메트릭이 있다.
- **오픈 소스**: 다차원 모델링과 PromQL을 지원하는 프로메테우스, 시계열 데이터 시각화에 특화된 그라파이트, SaaS 기반의 데이터독이 있다.
- **모범 사례**: 서비스 수준 목표에 직접 영향을 주는 핵심 메트릭에 집중하고, 일관된 이름 규칙을 쓰며, 오류율과 지연 시간을 우선 모니터링하고, 대시보드로 시각화한다.

## 8.7 분산 시스템에서 알림

- **알림**: 문제가 심각해지기 전에 잠재적 문제를 사전 감지하는 수단이다. 오류율이나 응답 시간, 리소스 사용량이 임계 값을 넘거나 특정 이벤트가 발생할 때 알림을 만든다.
- **효율적 설계**: 문제를 감지할 만큼 민감하면서도 거짓 경보로 알림 피로를 일으키지 않도록 정확성과 균형을 맞춘다. 중요도로 우선순위를 나누고, 실제 조치가 필요할 때만 알림을 만들며, 문제 진단에 필요한 정보를 충분히 담는다.
- **오픈 소스**: 중복 제거와 그룹화, 전달을 담당하는 프로메테우스 알림 매니저, 조건 기반 알림을 슬랙이나 웹훅으로 보내는 그라파나, 사고 관리 플랫폼인 페이저듀티가 있다.
- **모범 사례**: 임계 값을 조정해 알림 과다를 막고, 카오스 엔지니어링 등으로 알림이 제대로 작동하는지 테스트하며, 각 알림 유형의 대응 절차를 문서화한다.

## 8.8 분산 시스템에서 트레이싱

- **트레이싱**: 요청이 여러 서비스를 거쳐 처리되는 경로를 추적하는 기법이다. 서비스 간 상호 작용과 각 서비스의 지연 시간, 오류를 파악해 성능 문제를 진단하고 시스템 동작을 이해한다.
- **분산 트레이싱**: 요청이 처리되는 각 단계를 스팬(span)으로 기록하고, 스팬이 모여 요청 전체 흐름을 보여 주는 트레이스(trace)를 구성한다. 병목을 파악하는 성능 최적화, 실패 위치와 원인을 찾는 오류 진단, 요청 흐름을 파악하는 시스템 동작 이해가 장점이다.
- **오픈 소스**: 우버가 개발하고 구글 Dapper와 OpenZipkin에서 영감을 받은 예거(Jaeger), 서비스별 처리 시간을 수집해 지연을 분석하는 집킨(Zipkin), 트레이스와 메트릭 수집을 표준화하는 관측 프레임워크 오픈텔레메트리(OpenTelemetry)가 있다.
- **모범 사례**: 추적할 작업에 스팬을 설정해 코드에 트레이싱을 추가하고, 트레이스 컨텍스트를 HTTP 헤더로 서비스 간에 전파하며, 스팬 이름을 구체적이고 일관되게 짓고, 스팬에 메타데이터 주석을 더한다.

## 8.9 요약

- **API 설계**: REST와 gRPC는 각각 장점과 적합한 용도가 있어 성능과 사용 편의성, 호환성 등 요구 사항에 맞게 고른다.
- **API 보안**: 인증과 인가 메커니즘을 갖추고 HTTPS로 전송을 보호하며 요청 속도 제한으로 남용을 차단한다.
- **모니터링과 관측**: 중앙 집중형 로깅으로 로그를 모으고, 핵심 메트릭을 모니터링하며, 실효성 있는 알림으로 문제를 사전 포착하고, 분산 트레이싱으로 요청 흐름을 추적한다.
- 다음 장부터는 이 기본 요소들을 활용해 실제 시스템을 설계하고 구현한다.
