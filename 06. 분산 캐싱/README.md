# 06. 분산 캐싱

캐싱은 자주 쓰는 데이터를 애플리케이션이나 사용자와 가까운 고속 저장소에 임시로 두어 더 빠르게 접근하게 하는 기술이다. 애플리케이션이 여러 서버나 데이터 센터로 분산되면 단일 캐시만으로는 부족해 분산 캐싱이 필요하며, 이 장은 캐싱의 원리부터 분산 캐시 설계와 대표 솔루션까지 다룬다.

## 6.1 캐싱 정의

#### 주요 개념

- **캐싱**: 자주 사용하거나 계산 비용이 큰 데이터를 더 빠르게 접근할 수 있는 위치에 복사해 저장하는 기술이다. 데이터를 가져오는 시간과 자원을 줄이는 것이 목적이다.
- **캐시**: 자주 접근하는 데이터의 복사본을 임시로 담는 공간으로, 하드웨어(CPU 캐시)나 소프트웨어(인 메모리 캐시)로 구현된다.
- **캐시 히트와 캐시 미스**: 요청 데이터가 캐시에 있으면 히트라 원본 접근 없이 바로 반환하고, 없으면 미스라 원본에서 가져온 뒤 캐시에 저장한다.
- **캐시 제거(eviction)**: 캐시가 가득 차면 사용 빈도가 낮거나 오래된 데이터를 삭제해 새 데이터 공간을 확보한다.

#### 분산 캐싱

- **정의**: 자주 쓰는 데이터를 여러 서버나 노드의 메모리에 분산 저장하는 기술이다. 반복 조회를 원본 저장소 대신 캐시에서 처리해 응답 속도를 높이고 지연을 줄인다.
- **핵심 목표**: 디스크 기반 저장소의 읽기 속도 문제를 해결하는 데 있다. 자주 쓰는 데이터를 메인 메모리에 두어 디스크 입출력 없이 빠르게 가져온다.

#### 분산 캐싱과 일반 캐싱의 차이

- **일반 캐싱**: 자주 쓰는 데이터를 단일 시스템의 로컬 캐시에 저장하며, 같은 기기 안에서 실행되어 캐시에 바로 접근한다. 소규모 환경에 적합하고 일관성 유지가 단순하다.
- **분산 캐싱**: 캐시를 네트워크로 연결된 여러 노드로 확장한 방식으로, 노드 간 데이터를 공유하고 노드를 추가해 수평 확장한다. 대규모 웹 서비스나 마이크로서비스에 적합하지만 노드 간 동기화와 무효화가 복잡하다.

#### 활용 사례

- 웹 애플리케이션(사용자 세션, 페이지 구성 요소, 쿼리 결과), 자주 실행하는 데이터베이스 쿼리 결과, 정적 콘텐츠를 제공하는 CDN, 세션 관리, API 응답 캐싱, 실시간 분석 데이터, 메시지 큐의 중간 결과에 쓴다.

#### 장점

- **성능과 확장성**: 자주 쓰는 데이터를 메모리에 두어 접근 속도를 높이고, 부하가 늘면 캐시 노드를 추가해 쉽게 확장한다.
- **백엔드 부하 감소**: 자주 조회하는 데이터를 캐시가 대신 응답해 데이터베이스 부담을 덜고, DDoS 같은 상황에서 원본 서버 과부하 위험을 줄인다.
- **장애 허용성과 안정성**: 데이터 복제로 특정 노드가 죽어도 다른 노드가 처리하며, 데이터셋 크기와 무관하게 일정한 접근 속도를 제공한다.
- **비용과 사용자 경험**: 백엔드 부하가 줄어 추가 서버가 덜 필요해 인프라 비용을 아끼고, 응답이 빨라져 사용자 경험이 개선된다.

#### 한계점

- **일관성과 무효화**: 여러 노드의 데이터를 일관되게 유지하려면 동기화 메커니즘이 필요해 지연이 늘 수 있고, 원본이 바뀔 때 모든 노드의 캐시를 갱신하는 무효화 과정이 복잡하다.
- **운영과 네트워크**: 단일 노드 캐싱보다 설정과 관리가 어렵고, 노드 간 데이터 공유가 네트워크 부하를 일으킨다. 노드가 지리적으로 흩어질수록 심해진다.
- **오래된 데이터와 분배**: 동기화가 원활하지 않으면 갱신되지 않은 데이터를 반환할 수 있고, 분할 전략이 나쁘면 일부 노드에 과부하가 몰린다.
- **자원과 적합성**: 대량 데이터를 담으면 메모리 사용량과 비용이 커지고, 접근이 무작위이거나 빈도가 낮으면 유지 비용이 성능 이득을 넘어설 수 있다. 잦은 갱신이 필요한 쓰기 위주 환경보다 읽기 위주 환경에 적합하다.

## 6.2 분산 캐시 설계

#### 요구 사항

- **기능 요구 사항**: 키와 값 쌍을 추가하는 `put(key, value)`, 키로 값을 조회하는 `get(key)`를 지원해야 한다.
- **비기능 요구 사항**: 낮은 지연과 높은 처리량의 높은 성능, 노드를 추가해 대응하는 높은 확장성, 노드 장애에도 끊기지 않는 높은 가용성이다.

#### 캐시 데이터 구조

- **해시 맵**: 키와 값을 담는 해시 맵(해시 테이블)은 put과 get을 매우 빠르게 처리해 캐시 구현에 적합하다. 다만 크기가 서버 메모리를 초과하면 캐시 삭제 정책이 필요하다.

#### 캐시 삭제 정책

- **삽입 순서 기반**: 가장 오래된 항목을 삭제하는 선입선출(FIFO)과 가장 최근 항목을 삭제하는 후입선출(LIFO)이 있다.
- **접근 기반**: 가장 최근에 쓴 항목을 삭제하는 MRU, 가장 오래 쓰지 않은 항목을 삭제하는 LRU, 사용 빈도가 가장 낮은 항목을 삭제하는 LFU가 있다. LRU가 가장 일반적으로 쓰인다.

#### LRU 캐시 설계

- **요구 조건**: 저장 항목 수에 상한이 있고, 항목 추가와 삭제가 모두 O(1) 시간에 처리되어야 한다.
- **자료 구조**: 이중 연결 리스트와 해시 맵을 조합한다. 해시 맵은 키에서 리스트 노드로의 포인터를 담고, 리스트는 사용 순서를 유지한다.
- **읽기 흐름의 세 경우**: 캐시 미스이면서 공간이 있으면 원본에서 값을 가져와 노드를 만들어 리스트 맨 앞에 넣는다. 캐시 미스이면서 가득 차면 리스트 끝의 가장 오래된 항목을 삭제한 뒤 같은 과정을 따른다. 캐시 히트이면 해당 노드를 리스트 맨 앞으로 옮긴다. 세 경우 모두 O(1)에 처리된다.

#### 배포 전략

- **방법 1, 서버 통합형**: 캐시를 애플리케이션 서버와 같은 기기에 함께 둔다. 같은 기기 안의 프로세스 간 호출이라 조회가 빠르지만, 서버가 다운되면 다른 서버가 요청을 받아도 캐시가 비어 있는 문제가 있다.
- **방법 2, 스탠드얼론**: 캐시를 애플리케이션 서버와 분리해 독립된 클러스터에 배포한다. 애플리케이션과 무관하게 독립적으로 확장할 수 있지만, 캐시 키를 기준으로 데이터를 나눠야 해 일관된 해싱 같은 키 분배 전략이 필요하다.
- **선택 기준**: 성능 요구, 확장성, 자원 공유, 유연성, 의존성과 독립성, 운영 복잡성, 인프라 비용, 네트워크 지연 허용성을 종합해 결정한다. 네트워크 지연 최소화가 최우선이면 서버 통합형, 독립 확장과 유연성이 중요하면 스탠드얼론이 유리하다.

#### 요구 사항 점검

- **성능과 확장성**: 모든 연산이 O(1)이라 성능을 충족하고, 배포 서버 수를 늘려 샤딩하면 확장성도 충족한다.
- **가용성과 복제**: 한 서버가 다운되면 데이터를 잃을 위험이 있어 데이터 복제가 필요하다. 보통 주 복사본 하나에 보조 복사본 둘을 더해 서로 다른 서버에 세 개를 두고, 쓰기는 주 복사본에 먼저 저장한 뒤 보조 복사본으로 복제한다. 보조 복사본은 읽기 부하도 분담한다. 다만 복제는 가용성과 일관성 사이의 선택 문제를 낳는다.

## 6.3 대표적인 분산 캐시 솔루션

- **레디스(Redis)**: 문자열, 리스트, 집합, 해시 등 다양한 데이터 구조를 지원하는 인 메모리 데이터 저장소다. 영구 저장 옵션과 발행/구독 메시징, 트랜잭션, Lua 스크립팅 같은 고급 기능을 제공해 캐시뿐 아니라 메시지 브로커와 데이터베이스로도 쓰이며, 샤딩으로 확장한다.
- **맴캐시드(Memcached)**: 단순하고 직관적인 키-값 메모리 캐싱 솔루션으로 가볍고 쓰기 쉽다. 클러스터에 노드를 추가해 수평 확장하며 일관된 해싱으로 데이터를 여러 노드에 분산한다.

#### 선택 기준

- **사용 목적**: 레디스는 다양한 데이터 구조를 지원해 활용 범위가 넓고, 맴캐시드는 단순한 키-값 캐싱에서 빠르고 간단하다.
- **데이터 보존**: 레디스는 영구 저장 옵션이 있어 보존이 필요할 때 적합하고, 맴캐시드는 기본적으로 데이터를 영구 저장하지 않는다.
- **사용 편의성**: 맴캐시드는 단순한 설계로 통합과 운영이 쉽고, 레디스는 기능이 많은 대신 익숙해지는 데 시간이 더 걸린다.

## 6.4 요약

- **캐싱과 분산 캐싱**: 캐싱은 데이터 복사본을 빠른 위치에 저장하는 기술이고, 분산 캐싱은 이를 여러 노드로 확장해 대규모 환경의 성능 문제를 푼다. 디스크 기반 저장소의 속도 문제를 해결하는 데 효과적이다.
- **장단점**: 성능 향상, 확장성, 백엔드 부하 감소, 장애 허용성이 이점이고, 일관성 유지와 캐시 무효화, 운영과 네트워크 오버헤드가 한계다.
- **설계**: 기능과 비기능 요구 사항을 정의하고 해시 맵과 LRU 자료 구조를 고른 뒤, 배포 전략과 데이터 복제로 가용성까지 보완했다.
- **솔루션**: 기능이 풍부한 레디스와 단순하고 빠른 맴캐시드를 요구 사항에 맞게 고른다. 다음 장에서는 발행/구독 시스템과 분산 큐를 다룬다.
