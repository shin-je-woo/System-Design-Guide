# 04. 분산 시스템의 기본 요소: DNS, 로드 밸런서, 애플리케이션 게이트웨이

확장성 좋고 안정적인 분산 시스템을 떠받치는 세 요소를 다룬다.

- **DNS**: 도메인 이름을 IP로 변환해 글로벌 연결성을 확보한다.
- **로드 밸런서**: 여러 서버에 트래픽을 분산해 서버 성능을 최적화한다.
- **애플리케이션 게이트웨이**: 보안과 서비스 통합을 중앙에서 담당한다.

## 4.1 DNS 이해

- **DNS(Domain Name Server)**: 사람이 읽는 도메인 이름을 기계가 읽는 IP 주소로 변환하는 시스템이다. 브라우저가 도메인을 IP로 변환받아 그 주소의 목적지 웹 서버로 요청을 전달하며, 이 과정은 사용자 모르게 백그라운드에서 진행된다.

<img width="730" height="436" alt="image" src="https://github.com/user-attachments/assets/03eab0a3-6e4b-4c5d-99b5-75dafdae1c03" />

구성 요소

- **네임 서버(name server)**: 사용자 쿼리에 응답하는 DNS 서버다. DNS는 하나의 서버가 아니라 수많은 서버로 이뤄진 네트워크다.
- **리소스 레코드(resource record)**: 매핑 정보를 저장하는 단위다.
    - A: 도메인 이름을 IP에 매핑
    - NS: 도메인 요청을 처리할 권한 있는 네임 서버를 매핑
    - CNAME: 별칭 도메인을 정식 도메인에 연결
    - MX: 도메인을 메일 서버에 매핑
- **캐싱과 계층 구조**: 자주 쓰는 레코드를 캐싱해 대기 시간과 인프라 부하를 줄이고, 네임 서버를 계층으로 구성해 거대한 규모의 쿼리를 감당한다.

네임 서버 계층(위에서 아래로)

- **루트 서버**: 로컬 리졸버의 쿼리를 받아 .com, .org 같은 최상위 도메인 서버 정보를 관리한다.
- **최상위 도메인 서버(TLD)**: 해당 도메인의 권한 있는 네임 서버 IP를 보유한다.
- **권한 있는 네임 서버(authoritative name server)**: 조직이나 도메인의 최종 DNS 서버로 실제 IP 정보를 제공한다.
- **리졸버(resolver)**: 도메인 이름을 IP로 변환하도록 중개하는 요소이며, 보통 ISP나 회사 네트워크의 로컬 DNS 서버가 담당한다.

<img width="377" height="296" alt="image" src="https://github.com/user-attachments/assets/7e935e5f-c767-4fac-9b4f-956c7959a4ae" />

쿼리 방식

- **반복적 쿼리(iterative)**: 로컬 리졸버가 루트 → TLD → 권한 있는 네임 서버를 하나씩 직접 쿼리하며 IP를 찾는다. 단계마다 상태를 유지하지 않아 메모리 부담이 적고 인프라 부하 감소에 유리하다.
- **재귀적 쿼리(recursive)**: 사용자가 로컬 리졸버에 한 번 요청하면 리졸버가 나머지 과정을 대신 처리해 최종 IP를 전달한다. 일반적인 인터넷 사용에서 쓰는 방식이다.

기타

- **캐싱 위치**: 브라우저, 운영 체제, 로컬 네임 서버, ISP 리졸버 등 여러 단계에서 캐싱하면 응답 시간이 단축되고 전체 인프라의 쿼리 부하가 줄어든다.
- **환경 변수에 IP 대신 도메인을 쓰는 이유**: 서버 IP가 바뀌어도 코드를 고칠 필요가 없는 유연성, 한 도메인에 여러 IP를 연결하는 로드 밸런싱, TLS 인증서 검증이 가능한 보안 때문이다. IP 직접 사용은 DNS 쿼리를 건너뛰어 지연을 줄이지만 이 이점들을 잃는다.

## 4.2 DNS의 확장성, 신뢰성, 일관성

- **확장성**: 루트 → TLD → 권한 있는 네임 서버 계층으로 부하를 단계별 분산한다. 전 세계에 분산된 루트 서버 인스턴스 약 1000개와 중복 배치 덕분에 수십억 건의 쿼리를 처리하고, 한 서버가 죽어도 다른 서버가 대신 응답한다.
- **신뢰성**: 여러 단계의 캐싱과 전 세계 중복 서버로 확보한다. 대부분의 쿼리는 신뢰성이 낮은 UDP를 쓰지만, 응답이 없으면 요청을 재전송해 이를 보완한다.
- **일관성**: 강한 일관성 대신 높은 가용성을 우선한다. 캐시 유효 기간(TTL)과 점진적 업데이트 기반의 최종 일관성을 적용하며, 업데이트 반영에 몇 초에서 며칠이 걸린다.

## 4.3 로드 밸런서

- **역할**: 여러 서버와 자원에 작업을 고르게 분배해 처리량과 응답 시간을 개선하고 과부하를 막는다. 장애 서버의 요청을 정상 서버로 재전송해 내구성을 높이고, 일부 서버가 죽어도 가용성을 유지하며, 서버를 추가해 수평 확장한다.
- **위치**: 클라이언트와 프런트엔드 사이, 다층 구조의 계층 사이(웹-앱, 앱-DB), 여러 인스턴스를 가진 서비스 간에 배치해 각 계층을 독립적으로 확장하고 보호한다.
- **헬스 체크**: 정상 작동 중인 서버를 파악해 접근 불가한 서버로 요청이 가지 않게 막는다.
- **TLS 종료**: 백엔드 대신 복호화를 처리해 백엔드 부담을 덜고, 들어오는 트래픽의 보안 게이트웨이 역할을 한다.
- **트래픽 분석**: 요청 패턴을 분석해 서버 자원 활용을 극대화한다.

전역과 로컬

- **전역 서버 로드 밸런싱(GSLB)**: 사용자 위치와 데이터 센터 상태를 기반으로 여러 데이터 센터 간에 트래픽을 분산하고, 장애 시 자동으로 다른 센터로 전환한다.
- **로컬 로드 밸런싱**: 개별 데이터 센터 내부의 분산을 맡으며, 서버 상태와 용량 정보를 GSLB에 전달한다.
- **DNS 로드 밸런싱의 한계**: 여러 IP를 반환해 라운드 로빈으로 전역 분산은 되지만, 512바이트 패킷 제한으로 모든 IP를 담지 못하고, 클라이언트가 IP를 임의로 골라 과부하 센터로 갈 수 있으며, 가까운 서버를 판단하지 못하고, 긴 TTL 캐싱으로 복구가 느리다. 그래서 데이터 센터마다 로컬 로드 밸런서가 필요하다.

분배 알고리즘

- **라운드 로빈(round robin)**: 요청을 순차적으로 다음 서버에 할당하는 가장 간단한 방식이며, 서버 성능이나 현재 부하는 고려하지 않는다.
- **가중치 기반 라운드 로빈**: 서버 용량에 비례해 가중치를 부여하고, 용량이 큰 서버가 더 많은 요청을 받게 한다.
- **최소 연결**: 현재 연결 수가 가장 적은 서버에 새 요청을 할당해, 처리 시간이 긴 요청이 섞여도 부하를 고르게 나눈다.
- **최소 응답 시간**: 응답 시간이 가장 짧은 서버에 할당해 성능이 중요한 서비스의 효율을 높인다.
- **IP/URL/일관성 해시**: 클라이언트 IP나 요청 URL을 기준으로 특정 서버에 고정 할당하며, 특정 클라이언트나 URL을 같은 서버로 라우팅해야 할 때 쓴다.

세 가지 대비 축

- **정적 vs 동적**: 정적 알고리즘은 서버 상태를 실시간으로 반영하지 않아 간단하고, 동적 알고리즘은 현재 부하와 상태를 반영해 더 효과적이지만 상태 정보 유지에 통신 비용이 든다. 실무에서는 동적을 주로 쓴다.
- **스테이트풀 vs 스테이트리스**: 스테이트풀(stateful)은 세션 상태를 저장하고 공유해 신뢰성이 높지만 복잡하고 확장에 한계가 있고, 스테이트리스(stateless)는 일관된 해싱으로 매핑해 확장성이 좋지만 인프라 변경 시 안정성이 낮다. 실무에서는 둘을 혼합한다.
- **4계층 vs 7계층**: 전송 계층(4계층)은 TCP/UDP를 기준으로 연결을 유지하며 빠르게 분산하고, 응용 계층(7계층)은 HTTP 헤더, URL, 쿠키를 활용해 더 정교하게 분산한다. 실무에서는 둘을 병행한다.

배치 단계

- **0단계**: DNS로 여러 IP를 제공해 분산한다.
- **1단계**: 특수 라우터로 라운드 로빈이나 IP 기준으로 분배한다.
- **2단계**: 4계층 로드 밸런서로 같은 세션을 일관되게 전달한다.
- **3단계**: 7계층 로드 밸런서를 서버와 직접 연결해 상태를 모니터링하며 정교하게 분산한다.

## 4.4 애플리케이션 게이트웨이

- **정의**: 로드 밸런서보다 고도화된 프록시로, 클라이언트와 백엔드 사이에서 트래픽을 가로채 라우팅, 보안, 성능 가속, 분석을 지원한다. 여러 독립 서비스를 하나의 통합 API로 묶어야 하는 마이크로서비스 환경에서 특히 강점을 발휘한다.

<img width="515" height="451" alt="image" src="https://github.com/user-attachments/assets/2f10e6f9-e123-486d-a94e-8cdf39d82a25" />

주요 기능

- **고급 요청 라우팅**: 호스트 이름, 경로, 헤더, 요청 IP 등 조건에 따라 적합한 백엔드로 요청을 전달한다.
- **중앙 집중 보안**: 인증, 접근 제어, TLS 종료, DDoS 방어를 중앙에서 관리하고 웹 애플리케이션 방화벽(WAF)을 통합한다.
- **가속화와 오프로딩**: 캐싱, 압축, TCP TLS 오프로딩을 게이트웨이가 에지에서 대신 처리해 백엔드 부담을 덜어 준다.
- **모니터링**: 로그, 메트릭, 트레이스를 중앙에서 통합 수집해 애플리케이션 상태를 종합 파악한다.
- **적응성**: 요청과 응답을 조정해 레거시 서비스와의 연동 같은 변화를 유연하게 처리한다.

## 4.5 마이크로서비스 아키텍처

- **정의**: 하나의 큰 시스템을 독립적이고 재사용 가능한 여러 서비스로 나눠, 느슨하게 결합된 서비스들이 REST/HTTP 같은 가벼운 프로토콜로 통신하는 방식이다.

게이트웨이의 역할

- 여러 마이크로서비스를 하나의 논리적 API로 묶어 클라이언트가 백엔드 구현 변화에 직접 의존하지 않게 한다.
- 서비스 디스커버리와 동적 요청 라우팅으로 백엔드에 연결하고 인스턴스 간 로드 밸런싱을 지원한다.
- 인증이나 로깅, 보안 같은 횡단 관심사(cross-cutting concern)를 중앙에서 처리해 각 서비스의 중복 코드를 없앤다.

## 4.6 클라우드 네이티브 게이트웨이와 온프레미스 옵션

- **클라우드 관리형**: 주요 사업자가 완전 관리형 게이트웨이를 제공한다.
    - AWS: API Gateway, 애플리케이션 로드 밸런서
    - Azure: 응용 계층 로드 밸런싱, WAF, SSL 오프로딩
    - 구글 클라우드: DDoS를 방어하는 Cloud Armor, 캐싱용 Cloud CDN
    - 쿠버네티스: Istio, Kong, Traefik, Ambassador 같은 인그레스 컨트롤러
- **온프레미스 오픈 소스**: 금융처럼 자체 데이터 센터를 운영하는 기업이 선호하며, Kong, Tyk, NGINX, HAProxy가 대표적이다. 범용 인프라에서 실행돼 온프레미스 환경에서도 유연하게 구축할 수 있다.

## 4.7 요약

- **DNS**: 전 세계에 분산된 네임 서버 계층으로 도메인 이름을 IP로 변환하고, 반복적/재귀적 쿼리와 다단계 캐싱으로 확장성과 신뢰성을 확보하며 성능을 위해 최종 일관성을 택한다.
- **로드 밸런서**: 다양한 알고리즘으로 백엔드에 요청을 분산하고, 전역과 로컬, OSI 계층별로 트래픽을 조절해 성능과 가용성을 높인다.
- **애플리케이션 게이트웨이**: 고급 라우팅, 보안, 성능 최적화, 서비스 통합을 담당하며, 마이크로서비스의 흩어진 백엔드를 하나의 일관된 인터페이스로 묶는다.
